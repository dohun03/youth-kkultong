## 1. 서비스 개요

온통청년 공식 API에서 청년 정책을 수집하고, 사용자가 선택한 **분야·조건에 관련된 정책을 우선 보여주는** 웹 서비스다. 명확히 부적합한 정책만 제외하고, 확인된 조건의 일치 정도로 정렬한다. 실제 신청 자격은 공식 신청처의 안내를 기준으로 확인한다.

**사용 흐름:** 정책 목록 → 분야·조건 선택 → 제외 및 맞춤 정렬 → 상세 확인 → 신청·참고 링크 이동

## 3. 주요 기능과 MVP 범위

**MVP1 사용자 기능(완료·유지)**

| 기능 | 요구사항 |
| --- | --- |
| 정책 수집 | 온통청년 목록 API에서 정책을 수동 수집해 DB에 저장하고 실행 결과를 기록한다. |
| 정책 탐색 | 정책을 페이지별로 제공한다. 분야, 사용자 조건, 마감 포함 여부, 정렬 기준을 선택할 수 있다. |
| 맞춤 결과 | 명확히 부적합한 정책을 제외하고, 일치한 항목을 태그로 표시하며 맞춤 점수로 정렬한다. |
| 정책 상세 | 정책 설명·지원 내용·자격 조건·신청기간·신청/참고 링크를 보여준다. 링크가 없으면 ‘링크 없음’으로 표시한다. |
| 사용자 입력 | 나이, 거주지역, 취업 상태, 학력을 선택적으로 입력받아 브라우저에서 관리한다. |

MVP1의 구현·검증 결과와 완료 기준은 `mvp-1/SUMMARY.md`를 따른다.

**MVP2 기능(완료·유지):** 기존 정책 탐색을 유지하면서 매일 수집한 신규·변경 내용을 관리자가 확인한 뒤 공개한다.

| 기능 | MVP2 범위 |
| --- | --- |
| 자동 수집 | 기존 온통청년 API를 매일 전체 수집하고 수동 실행도 유지한다. 실행 결과와 실패 원인을 기록한다. |
| 데이터 분리 | 최신 수집 원본, 검수 후보와 처리 이력, 사용자에게 제공하는 공개 정책을 분리한다. |
| 관리자 웹 UI | 검수 대기 목록·상세, 기존 공개본과 변경본 비교, 승인·거절, 처리 이력 및 누락 정책 확인을 제공한다. 신규 후보는 공개본이 없는 상태로 표시한다. |
| 관리자 접근 | 최소한의 관리자 인증과 모든 관리자 API의 서버 측 권한 검증을 적용한다. 일반 사용자 계정 없이 운영한다. |
| 기존 데이터 이관 | 기존 정책은 승인된 공개 데이터로 간주한다. 기존 UUID와 공개 API 동작을 유지하며 검수 대기열에 일괄 등록하지 않는다. |

**MVP2 제외 범위:** 추가 정책 API, 일반 회원가입·로그인·회원 관리, 복잡한 관리자 권한 체계, 자동 정책 삭제·비공개, Redis·BullMQ·별도 Worker(상시 작업 프로세스).

**MVP2 완료 결과:** 자동 수집과 실패 기록, 신규·변경 검수 및 승인 후 공개, 중복 검수 방지, 누락 추적, 기존 공개 정책·탐색 기능 유지를 구현·검증했다. 완료 근거는 `mvp-2/SUMMARY.md`, 운영 정책은 7장을 따른다. 자동 수집은 API가 계속 실행되는 환경에서 동작하며, 스케줄 등록·검증과 운영 환경의 개별 예약 실행 성공은 구분한다.

### 3.1 MVP3 목표와 범위

관리자가 대량의 신규 정책과 변경 정책을 효율적으로 검수하고, 웹에서 수집을 실행하고 결과를 확인할 수 있도록 운영 편의를 개선한다. 기존 사용자 탐색과 MVP2의 수집, 후보 생성, 승인과 거절 정책을 유지한다.

### 3.2 변경 중요도

`CHANGED` 검수 후보에 **중요 / 일반 / 경미**를 부여하고, `NEW` 후보는 **신규**로 구분한다. 기준은 **변경된 온통청년 API 원본 필드가 사용자의 신청 판단과 행동에 주는 영향**이다. 후보 생성 당시 공개본과 변경본의 원본을 비교하며, 여러 필드가 바뀌면 가장 높은 등급을 적용한다.

| 등급 | 기준과 대상 |
| --- | --- |
| 중요 | 신청 가능 여부, 혜택, 신청 행동에 직접 영향. 신청기간, 지원 자격, 지원 내용, 신청 URL, 신청 방법, 제출서류, 심사 절차 등 |
| 일반 | 정책 식별, 이해, 탐색과 추가 안내 확인에 영향. 제목, 설명, 분야, 참고 URL 등 |
| 경미 | 신청 판단과 직접 관련 없는 명확한 메타정보. 정책 키워드, 원본 등록 시각과 수정 시각 등 |

미분류 필드는 **중요**로 처리하고, 상세에 미분류 필드가 포함됐음을 표시한다. 등급은 필드 종류로 결정하므로 지원 내용의 오탈자 수정도 중요에 해당한다. 필드 추가와 삭제도 변경으로 계산하며, 조회수는 기존 비교 규칙을 유지한다.

중요도는 검수 우선순위를 위한 안내이며 내용의 정확성이나 신청 자격을 보증하지 않는다. 기존 변경 해시, 후보 생성과 승인 또는 거절 규칙을 유지한다. 전체 원본 필드의 **필드명 / 의미 / 등급 / 분류 이유**는 구현 전에 MVP3 SPEC에서 확정한다.

### 3.3 관리자 검수 대기 목록

제목 검색을 유지하고, 유형과 변경 중요도를 별도 필터로 제공한다.

| 필터 | 선택지와 동작 |
| --- | --- |
| 유형 | 전체 / 신규 / 변경 |
| 변경 중요도 | 전체 / 중요 / 일반 / 경미. 특정 중요도를 선택하면 해당 변경 후보를 조회 |

유형이 전체 또는 변경이면 두 조건을 함께 적용한다. 유형을 신규로 바꾸면 중요도를 전체로 초기화하고 비활성화한다. 목록에는 **신규**, **변경 [중요]**, **변경 [일반]**, **변경 [경미]**로 표시한다.

기본 정렬은 **중요도순**이다.

| 정렬 | 기준 |
| --- | --- |
| 중요도순 | 중요 → 신규 → 일반 → 경미. 같은 그룹에서는 후보 생성 시각이 오래된 순 |
| 오래된 순 | 후보 생성 시각이 오래된 순 |
| 최신순 | 후보 생성 시각이 최신인 순 |

중요도순은 이미 공개된 정책의 중요한 변경을 먼저 확인하고, 다음으로 미공개 신규 정책을 검수하는 순서다.

- 검색, 필터, 정렬을 전체 대기 후보에 적용한 뒤 페이지를 나눈다.
- 표시 개수는 **20 / 50 / 100건** 중 선택하며, 후보 생성 시각을 기준으로 대기 기간을 보여준다.
- 검색어, 필터, 정렬, 표시 개수, 현재 페이지를 `sessionStorage`에 보관해 상세 복귀와 새로고침 시 복원한다. 체크박스 선택은 화면 메모리에서만 관리한다.

### 3.4 일괄 승인·거절

- 현재 페이지의 후보를 개별 체크하거나 전체 선택해 한 번에 최대 **100건**을 처리한다. 페이지 이동·필터 변경 시 선택을 초기화한다.
- 승인·거절 모두 확인 모달을 사용한다. 승인은 **선택 건수 확인 → 최종 승인 → 항목별 결과**, 거절은 **선택 건수 확인 및 공통 거절 사유 입력 → 최종 거절 → 항목별 결과** 순서로 진행한다.
- 공통 거절 사유는 각 후보의 기존 `rejection_reason`에 개별 저장한다. 거절 확인에는 **같은 내용 해시가 다시 수집돼도 자동 재검수되지 않는다**는 영향을 안내한다.
- 후보마다 기존 개별 검수와 같은 조건으로 처리한다. 일부가 실패해도 성공한 후보는 유지하며, 성공·충돌·실패 건수와 후보별 오류 원인을 화면에 표시한다.
- 오래된 화면이나 중복 요청으로 이미 처리된 후보를 다시 바꾸지 않는다. 응답 유실 등으로 처리 여부가 불명확하면 후보별 최종 상태를 다시 확인하도록 하고, 확인 전 일괄 요청을 자동 재전송하지 않는다. 확인되지 않은 결과는 실패로 단정하지 않는다.

### 3.5 관리자 웹 수동 수집과 운영 상태

- 관리자 화면에 기존 온통청년 수집을 실행하는 버튼을 제공한다. 관리자 인증과 요청 출처(Origin) 검사를 통과한 요청만 접수한다.
- 완료까지 HTTP 연결을 유지하지 않는다. 실행 요청 접수 후 실행 ID로 상태를 조회하며, 이미 수집 중이면 중복 실행을 막고 현재 상태를 안내한다.
- 실행 상태는 서버에서 관리한다. 새로고침·화면 이동 후에도 현재 실행과 마지막 결과를 다시 조회할 수 있어야 한다.
- 현재 수집 중 여부, 마지막 실행 시각과 결과, 마지막 정상 수집 시각을 보여준다. 완료 후 신규·변경·동일·누락 건수, 실패 단계와 안전하게 표시할 수 있는 오류 원인을 제공한다.
- 실행 결과와 **DB 반영 완료 / 미반영 / 결과 확인 불가**를 구분한다. API 재시작·비정상 종료나 응답 유실만으로 실제 실패 또는 미반영을 단정하지 않는다. DB 반영 후 로그·정리 오류도 이미 반영된 결과와 구분해 안내한다.
- 기존 CLI·Cron·웹 실행은 같은 수집 서비스를 사용한다. 단일 API 프로세스 안에서 실행하므로 API 중단 시 수집도 중단될 수 있으며, 자동 재개·누락 실행 보충은 제공하지 않는다.

### 3.6 MVP3 제외 범위와 완료 기준

**제외 범위:** 추가 정책 API 연동(MVP4 이후 검토), LLM 연동, 일반 회원가입·로그인·프로필, 검수 자동 승인, 정책 직접 수정 및 자동 삭제·비공개, 거절된 검수의 자동 재개방, 수집 중 취소·강제 롤백, Redis·BullMQ·별도 Worker 등 작업 인프라 확장, 복잡한 관리자 권한 시스템, 복잡한 모니터링 대시보드·전체 로그 검색 시스템.

**완료 기준:** 중요도에 따라 전체 대기열을 탐색하고 목록 상태를 복원할 수 있으며, 확인을 거친 일괄 검수의 부분 성공과 항목별 결과를 확인할 수 있어야 한다. 웹 수집은 중복 실행을 방지하고 화면 재진입·API 재시작 이후에도 실행 여부와 확인 가능한 결과를 일관되게 안내해야 한다. 기존 공개 정책·탐색과 MVP2 검수 안전성은 유지한다.

## 4. 정책 목록·필터·정렬

### 4.1 목록 카드와 상세 이동

목록 카드에는 다음을 표시한다.

| 정보 | 표시 방식 |
| --- | --- |
| 정책명·분야 | 제목과 대분류(주거·일자리·교육·복지 등). 필요한 경우 중분류 표시 |
| 정책 소개 | API 정책 설명(`plcyExplnCn`)을 정제한 짧은 소개를 제목 아래 최대 두 줄로 표시. 지원 혜택과 자세한 조건은 상세에서 확인 |
| 신청 상태·기간 | ‘상시 / 접수 예정 / 신청 가능 / 마감 임박 / 마감 / 확인 필요’와 확인 가능한 신청 날짜 |
| 조건 관련 정보 | 조건 입력 시 ‘나이 기준 부합’, ‘취업 상태 부합’, ‘학력 부합’, ‘지역 관련’, ‘추가 조건 확인’ 등 실제 확인된 태그 |
| 조회수 | 온통청년 API의 `inqCnt` 기준 조회수 |

정책 카드를 선택하면 DB에 저장된 해당 정책의 상세 페이지로 이동한다. 상세 페이지에서 지원 대상·내용·자격 조건 및 신청·참고 링크를 확인할 수 있다.

### 4.2 필터와 기본 정렬

복수 분야는 쉼표로 분리해 선택지 중복을 제거하고, 한 정책이 여러 분야에 속하면 해당 분야 각각에서 조회한다. DB 원문은 보존하며 세부 규칙은 MVP1 SPEC 8.3을 따른다.

정책명 검색창에서 제목에 포함된 단어로 검색한다. 버튼/Enter로 실행하고 적용 검색어를 탭 세션에 유지한다. 검색 대상은 제목이며 세부 비교 규칙은 MVP1 SPEC 4.1·8.1을 따른다.

목록 표시 개수는 10·20·50개 중 선택해 탭 세션에 유지한다. 변경 시 1페이지로 이동한다. 결과 총 건수와 상단 페이지 이동을 제공한다. 기존 표시·색상 규칙은 MVP1 SPEC 8장을 유지한다.

나이·지역·취업·학력과 분야·마감 포함·직접 선택한 정렬은 탭 세션에 유지해 새로고침·상세 복귀 후 복원한다. 페이지는 1페이지로 시작하며 복원 검증과 정렬 예외는 MVP1 SPEC 8.1절을 따른다.

- **분야:** 기본은 ‘전체’. 온통청년의 대분류(`lclsfNm`)를 기준으로 주거·일자리·교육·복지 등 실제 제공되는 분야를 노출한다.
- **사용자 조건:** 나이, 거주지역, 취업 상태, 학력 중 필요한 항목만 선택한다.
- **마감 포함:** 기본 해제. 선택하면 마감 정책도 함께 표시한다. 다른 신청 상태는 기본 노출한다.
- **정렬:** 사용자 조건이 없으면 **인기순**, 하나라도 입력하면 기본 **맞춤순**이다. 조건이 없을 때 맞춤순은 선택할 수 없으며, 조건을 지우면 인기순으로 전환한다. 인기순·마감순·최신순 직접 선택은 조건 유무와 관계없이 유지한다.

| 정렬 옵션 | 정렬 기준 |
| --- | --- |
| **맞춤순** | 지역 입력 시 지역 관련 우선 → 기존 맞춤 점수 높은 순 → 마감 임박 우선 → 조회수 높은 순(지역 미입력 시 지역 우선 기준 생략) |
| **인기순** | 조회수(`inqCnt`) 높은 순 |
| **마감순** | 접수 중인 정책의 종료일이 가까운 순 → 접수 예정 정책의 시작일이 가까운 순 → 상시·확인 필요 → 마감 정책 |
| **최신순** | 최초 등록일(`frstRegDt`) 최신순 |

정렬값이 같으면 최초 등록일 최신순, 정책 식별자순으로 순서를 고정한다. **전체 정책에 분야·마감·조건 필터와 제외 판정을 적용한 다음 정렬하고, 마지막에 페이지를 나눈다.** 페이지를 넘겨도 필터·정렬 기준은 유지한다.

## 5. 신청 상태

온통청년의 `aplyPrdSeCd`(신청기간 구분 코드)와 `aplyYmd`(신청 시작·종료일 문자열)를 함께 해석한다.

| 상태 | 표시 기준 |
| --- | --- |
| **상시** | 상시 접수로 확인됨 |
| **접수 예정** | 신청 시작일이 현재 날짜보다 미래 |
| **신청 가능** | 신청기간 중이고 마감일까지 8일 이상 남음 |
| **마감 임박** | 신청기간 중이고 **마감일까지 7일 이하** 남음(마감일 포함) |
| **마감** | 종료일이 지났거나 API에서 마감으로 확인됨 |
| **확인 필요** | 날짜 누락·복수 기간·날짜 역전 등 신청 상태를 확정할 수 없음 |

**판정 순서:** API의 명시적 마감 → 명확한 상시 접수 → 유효한 시작·종료일에 따른 상태 계산 → 확인 필요. 남은 일수는 한국 시간의 날짜를 기준으로 계산한다. 신청 상태는 화면의 안내 정보이며 실제 접수 가능 여부는 신청처에서 확인한다.

## 6. 조건 판단과 맞춤 점수

### 6.1 제외·확인 규칙

나이·취업 상태·학력의 구조화된 자격 조건으로 판단한다. **정책 조건이 확실히 불일치할 때만 목록에서 제외**하며, 그 외에는 정책을 보여준다.

| 내부 판단 | 처리 |
| --- | --- |
| `MATCHED`(조건 부합) | 확인한 해당 항목이 정책 기준에 부합 |
| `EXCLUDED`(명확한 불일치) | 신뢰할 수 있는 조건이 입력과 충돌하여 정책 제외 |
| `UNKNOWN`(확인 필요) | 조건·사용자 정보·예외 해석이 불충분하여 정책 유지 및 확인 항목 표시 |

화면에서는 정책 전체의 `MATCHED / UNKNOWN`을 주된 강조 요소로 쓰기보다, **어떤 항목이 부합하는지와 무엇을 확인해야 하는지**를 태그로 보여준다. 입력하지 않은 항목은 일치 태그나 점수로 계산하지 않는다.

| 항목 | API 근거 | 판단 방식 |
| --- | --- | --- |
| 나이 | `sprtTrgtMinAge`, `sprtTrgtMaxAge` | 정상적인 범위(`0 < 최소 ≤ 최대`)와 입력 나이를 비교한다. `0~0`·이상치·빈 값은 `UNKNOWN`. |
| 취업 상태 | `jobCd` | 확인된 코드와 사용자 선택을 비교한다. ‘제한없음’(`0013010`)은 제한 없음으로 처리한다. |
| 학력 | `schoolCd` | 확인된 코드와 사용자 선택을 비교한다. ‘제한없음’(`0049010`)은 제한 없음으로 처리한다. |
| 거주지역(참고) | `zipCd` | 공식 시·군·구 코드와 상위 시·하위 구 관계를 비교하여 지역 연관성을 표시한다. |

- 같은 항목에 여러 **허용 코드**가 있을 때는 OR(하나라도 부합하면 통과), 서로 다른 자격 항목은 AND(각 항목 충족)로 계산한다. 이는 구조화된 코드에 적용하는 MVP1 규칙으로, 코드 뜻·관계가 불명확하면 `UNKNOWN`이다.
- 문장으로 적힌 추가 자격·참여 제한(`addAplyQlfcCndCn`, `ptcpPrpTrgtCn`)이 있으면 예외 가능성을 표시하고, 구조화 조건의 불일치만으로 정책을 제외하지 않는다.
- 거주지역은 **참고·정렬용**으로 사용한다. 코드에 기재된 지역이 실제 신청 가능한 거주지와 일치한다고 검증되지 않았기 때문이다.
- 현재 행정구역 코드와 명칭으로 지역을 선택하며, 선택 지역과 같은 지역·상위·하위 지역을 공식 부모 관계로 비교한다. 형제 지역은 포함하지 않는다. 폐지 코드만 있는 정책은 ‘지역 확인 필요’로 표시한다.

### 6.2 맞춤 점수

**사용자가 입력한 조건 중 실제로 확인된 부합 항목만 가점**한다. 제한 없는 항목과 판단 불가 항목에는 점수를 부여하지 않는다.

| 항목 | 확인된 부합 시 가점 |
| --- | ---: |
| 나이 | +1점 |
| 취업 상태 | +1점 |
| 학력 | +1점 |
| 지역 코드상 연관성 | +0.5점 |

- 예: 나이 부합(+1), 취업 상태 부합(+1), 학력 제한 없음(+0), 지역 관련(+0.5) → **2.5점**.
- `UNKNOWN`은 **0점**으로 남겨 둔다. 가점이 적다는 이유로 정책을 제외하지 않는다.
- 지역의 +0.5점은 자격 부합 점수가 아닌 **탐색 관련성 가점**이다. 화면에는 ‘지역 관련’으로 구분한다.
- 정책 전체에 확인할 조건이 남아 있어도, 별도로 확인된 부합 항목은 정렬 점수에 반영한다. 단, 화면에서 최종 신청 가능 여부로 표현하지 않는다.
정렬은 4.2절을 따른다. ‘지역 관련’은 자격 확정이 아니며, 재학·재직·전입 조건은 상세에서 확인하도록 안내한다.

## 7. 수집 및 데이터 처리

### 7.1 수집과 보관

- 온통청년 API를 NestJS `@Cron`으로 매일 한국 시간 04:00에 전체 수집하며 수동 실행도 유지한다. API 서버가 실행 중일 때 동작하고 중지 중 누락된 실행은 복구 후 수동 수집한다. 기존 호출·검증·정규화 규칙을 재사용한다.
- 정책은 출처와 외부 정책 ID로 구분한다. **지난 수집 원본과 이번 내용을 비교**해 `NEW`(신규) / `CHANGED`(변경) / `UNCHANGED`(동일)를 판단한다. 정상 전체 수집에 없는 기존 정책은 `MISSING`(누락)이다. 수집 결과는 검수 상태와 별개다.
- 최신 원본, 검수 당시 내용과 처리 이력, 사용자에게 공개할 정책을 분리해 보관한다. 테이블 역할은 아키텍처 5.3절에 정의한다.
- 전체 수집·검증에 성공한 결과만 반영한다. 실패하면 기존 데이터와 누락 횟수를 유지하고 실패 원인을 기록한다.
- 누락은 삭제 확정이 아니다. 정상 수집에서의 연속 누락 횟수를 관리자에게 보여주고 다시 수집되면 해제한다. 자동 삭제·비공개하지 않는다.
- 조회수는 내용 비교에서 제외하고 승인 여부와 관계없이 공개 정책에 갱신한다. 미승인 본문·조건·기간·링크는 공개하지 않는다.

### 7.2 검수와 공개

- 신규·변경 내용은 `PENDING`(검수 대기)으로 등록한다. 관리자가 승인하면 `APPROVED`(승인)로 기록하고 검수한 내용을 공개한다. 거절하면 `REJECTED`(거절)로 기록하고 기존 공개본을 유지한다. 신규는 승인 전까지 공개하지 않는다.
- 대기 중 내용이 또 바뀌면 이전 후보를 `SUPERSEDED`(대체됨)로 남기고 필요한 최신 후보만 대기로 둔다. 같은 내용을 반복 수집해 후보를 중복 생성하거나 과거 내용을 덮어쓰지 않는다.
- 현재 공개본과 같은 내용이나 이미 거절한 내용은 다시 대기로 등록하지 않는다. 거절 후 다른 내용이 수집되면 새 검수 대상으로 판단한다. 과거 승인·대체된 내용으로 돌아왔어도 현재 공개본과 다르면 새 검수가 필요하다. 과거 승인만으로 자동 복원하지 않는다.
- 승인 직전에 최신 원본과 현재 공개본이 검수 기준과 같은지 확인한다. 달라졌으면 승인을 중단해 오래된 내용이 덮어쓰지 않게 한다. 해시 비교·동시 처리의 상세 기준은 MVP2 SPEC 6장을 따른다.
- MVP1 기존 정책은 승인된 공개 데이터로 간주한다. 공개 UUID·내용을 유지하고 검수 대기나 실제로 없었던 승인 이력을 만들지 않는다. 이관 시각과 실제 API 수집 시각은 구분한다.

## 9. 개발 진행 순서

1. **PRD·ARCHITECTURE:** 완료된 MVP1·MVP2 구현을 기준으로 MVP3 제품 범위·운영 정책·구조를 확정한다(이번 작업).
2. **MVP3 SPEC:** 합의한 분류와 정렬 기준에 따라 전체 필드 매핑, 필터 조합과 정확한 정렬 규칙, API 요청과 응답, DB 컬럼과 제약조건, 실행 상태 전이, 동시성과 오류 예외, 테스트 시나리오를 정의한다. 기존 MVP2 규칙의 유지 또는 확장 범위를 명시한다.
3. **MVP3 PLAN:** 확정된 SPEC에 따라 목록 개선·일괄 검수·웹 수집과 상태 조회의 작업 순서 및 완료 조건을 작성한다.
4. **구현·검증:** PLAN에 따라 진행하고 기존 공개 API·탐색·검수·수집 운영의 호환성을 함께 검증한다. 이번 문서 수정은 SPEC·PLAN 작성이나 기능 구현 완료를 뜻하지 않는다.
