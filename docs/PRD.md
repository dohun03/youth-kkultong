# 청년꿀통 PRD v0.4

> 정부·지자체 지원 정책을 한곳에서 보고, 내 조건을 입력할수록 나에게 맞는 정책을 더 정확하게 찾을 수 있도록 돕는 서비스  
> 초기 방향: 브라우저 기반 웹 서비스 우선 / 모바일 앱 및 정식 대규모 출시는 후순위

---

## 1. 서비스 개요

### 1.1 한 줄 설명

지원 정책 전체를 먼저 보여주고, 사용자가 나이·지역·상태·소득 등의 정보를 선택적으로 입력하면 조건에 맞는 정책으로 결과를 좁혀주는 서비스다.

### 1.2 해결하려는 문제

정부와 지자체의 지원 정책은 여러 사이트에 흩어져 있고, 공고마다 조건 표현 방식도 달라 사용자가 직접 자신에게 맞는 정책을 찾기 어렵다.

기존 서비스들은 처음부터 회원가입이나 많은 개인정보 입력을 요구하는 경우가 있어 사용자가 실제 가치를 경험하기 전에 이탈할 수 있다.

청년꿀통은 먼저 정책을 자유롭게 둘러보게 하고, 필요한 정보만 선택적으로 입력하면서 결과를 정교하게 만드는 것을 목표로 한다.

---

## 2. 핵심 제품 원칙

1. **로그인 없이 먼저 사용할 수 있어야 한다.**
2. **처음에는 모든 활성 정책을 보여준다.**
3. **사용자가 조건을 입력할수록 결과가 더 정확해진다.**
4. **입력하지 않은 정보 때문에 정책을 임의로 탈락시키지 않는다.**
5. **확실하지 않은 자격 조건을 추측해서 충족이라고 판단하지 않는다.**
6. **로그인은 정책 검색이 아니라 저장·북마크·알림 등 개인화 기능을 위한 부가 기능이다.**
7. **초기에는 정책 수집 자동화보다 실제 정책을 이용한 검색·매칭 경험 검증이 우선이다.**

---

## 3. 핵심 사용자 경험

### 3.1 최초 접속

사용자는 로그인하지 않아도 바로 정책 목록을 볼 수 있다.

```text
웹 접속
↓
현재 신청 가능한 정책 전체 보기
↓
관심 있는 정책 직접 탐색
또는
조건 몇 개 입력
↓
조건에 맞지 않는 정책 제거
↓
조건을 더 입력할수록 결과가 정교해짐
↓
정책 상세 확인
↓
공식 공고 이동
```

### 3.2 선택 정보 입력

사용자 정보는 처음부터 전부 요구하지 않는다.

예:

- 지역만 선택
- 나이만 입력
- 지역 + 나이
- 지역 + 나이 + 현재 상태
- 지역 + 나이 + 상태 + 가구원 수 + 소득

어떤 조합이든 사용할 수 있다.

사용자가 입력하지 않은 항목은 **미입력 상태**로 두며 해당 조건 때문에 정책을 제거하지 않는다.

### 3.3 로그인 시점

로그인은 핵심 검색 기능 이용에 필요하지 않다.

사용자가 서비스의 가치를 경험한 후 다음 기능을 사용하고 싶을 때 로그인한다.

- 입력한 조건 저장
- 북마크
- 관심 정책 관리
- 마감 알림
- 캘린더
- 새 정책 알림

## 4. 정책 목록

### 4.1 첫 화면

첫 화면에는 현재 노출 가능한 정책을 전체 목록으로 보여준다.

정책 수가 많아질 경우 pagination 또는 무한 스크롤을 사용할 수 있지만 사용자 경험상 첫 화면은 "전체 정책 탐색"이 기준이다.

### 4.2 정책 카드 주요 정보

목록에서는 최소한 다음 정보를 보여준다.

| 항목 | 설명 |
|---|---|
| 정책 이름 | 정책명 |
| 지원 금액 | 최대 총 지원 금액 또는 대표 지원 내용 |
| 신청 기간 | 시작일, 마감일, 상시 여부 |
| 카테고리 | 교육, 주거, 복지, 취업, 금융 등 |
| 지역 | 전국, 시/도, 시/군/구 |
| 나이 | 대표 나이 조건 |
| 지급처 | 담당 기관, 지자체, 공공기관 등 |

추가로 필요하면 다음을 보여줄 수 있다.

- 신청 예정
- 마감 임박
- 조건 확인 필요
- 마지막 정책 확인일

### 4.3 정책 상세

정책 카드를 누르면 상세 화면으로 이동한다.

상세 화면에서는 다음을 보여준다.

- 정책명
- 지원 금액 및 지원 내용
- 담당 기관
- 신청 기간
- 지원 대상
- 나이 조건
- 지역 조건
- 소득 조건
- 기타 자격 조건
- 제출 서류
- 신청 방법
- 공식 공고 링크
- 마지막 확인일

서비스는 자격을 확정하지 않으며 최종 신청 전 공식 공고를 확인하도록 안내한다.

## 5. 검색과 매칭 개념

### 5.1 기본 상태

사용자가 아무 정보도 입력하지 않았다면 모든 활성 정책을 보여준다.

### 5.2 사용자가 조건을 입력한 경우

입력된 항목에 대해서만 정책 조건과 비교한다.

예:

```text
지역 = 서울
```

이라면 서울에서 신청할 수 없는 정책을 제외한다.

여기에

```text
나이 = 27세
```

를 추가하면 서울 정책 중 27세가 신청할 수 없는 정책을 추가로 제외한다.

### 5.3 미입력과 판단 불가를 구분한다

다음 둘은 다른 상태다.

**사용자 미입력**

> 사용자가 소득을 입력하지 않았다.

이 경우 소득 조건 때문에 정책을 제거하지 않는다.

**정책 판단 불가**

> 정책의 소득 기준 자체가 복잡하거나 현재 시스템에서 정확히 판단할 수 없다.

이 경우 해당 조건에 대해 "직접 확인 필요"라고 표시한다.

### 5.4 매칭 정확도

정보를 더 입력한다고 "당첨 확률"이 올라가는 것이 아니다.

정확한 표현은:

> 사용자가 정보를 더 입력할수록 자신과 맞지 않는 정책을 더 많이 제외할 수 있어 결과의 정확도가 높아진다.

---

## 6. 정책 조건

초기에는 다음 조건을 중심으로 구조화한다.

- 나이
- 지역
- 현재 상태
- 가구원 수
- 소득
- 신청 기간
- 별도로 자동 판단하지 못하는 추가 자격 조건

모든 정책 조건을 완벽하게 자동 판정하려 하지 않는다.

시스템에서 확실히 판단할 수 없는 조건은 정책을 잘못 제외하거나 충족시키지 않고 사용자에게 확인 필요로 안내한다.

# 7. MVP 로드맵

## MVP 0 — 실제 정책 데이터 준비

### 목표

코드를 복잡하게 만들기 전에 실제 정책 데이터로 서비스 핵심을 테스트할 준비를 한다.

### 구현

- 정책 데이터 모델 정의
- 실제 정책 30~50건 선정
- 공식 공고 기준으로 정책 직접 정리
- JSON 파일 작성
- JSON → PostgreSQL import
- 공식 공고 URL 저장
- 테스트용 정책 조회 기능

### 하지 않는 것

- 로그인
- 사용자 프로필
- 관리자 화면
- 자동 수집
- LLM
- 알림

### 완료 기준

- 실제 정책 30~50건이 DB에 들어가 있다.
- 각각 공식 공고 주소가 있다.
- 나이·지역·금액·기간 등 핵심 데이터가 구조화되어 있다.

---

## MVP 1 — 정책 탐색과 선택형 매칭

### 목표

**"로그인하지 않고도 내게 맞는 지원 정책을 쉽게 찾을 수 있는가?"**

를 검증한다.

### 핵심 기능

- 전체 정책 목록
- 정책 카드
- 정책 상세
- 카테고리 필터
- 지역 조건
- 나이 조건
- 현재 상태
- 선택형 가구원 수
- 선택형 소득 입력
- 입력 조건에 따른 정책 필터링/매칭
- 조건 초기화
- 공식 공고 이동

### 사용자 흐름

```text
접속
↓
전체 정책
↓
조건 선택
↓
결과 즉시 좁히기
↓
정책 상세
↓
공식 공고
```

### 로그인

없음.

### 정책 입력 방식

MVP 0에서 만든 JSON import를 계속 사용한다.

관리자 화면도 필수로 만들지 않는다.

### 핵심 검증

- 사용자가 원하는 정책을 실제로 찾는가?
- 조건 입력 과정이 어렵지 않은가?
- 어떤 조건을 가장 많이 사용하는가?
- 확인 필요 정책이 지나치게 많지 않은가?
- 잘못 제외되거나 잘못 추천되는 정책이 있는가?

## MVP 2 — 정책 수집 및 운영 자동화

### 목표

수동으로 정책을 추가하고 갱신하는 부담을 줄인다.

### 핵심 기능

- 공공 API 연동
- 신규 정책 자동 수집
- 원문 데이터 저장
- Raw HTML/Text Sanitizer
- 정책 변경 감지
- 사라진 정책 감지
- 정책 마지막 확인 상태 관리
- 운영자 정책 목록
- 운영자 정책 등록/수정
- 공개/비공개
- 정책 재확인
- 정책 데이터 변경 기록

### 운영 방식

```text
공공 API
↓
원문 수집
↓
정제
↓
운영자가 확인
↓
구조화된 정책으로 저장
↓
사용자에게 공개
```

LLM은 아직 사용하지 않는다.

## MVP 3 — 로그인과 개인화

### 목표

서비스가 유용하다고 느낀 사용자가 자신의 정보를 저장하고 계속 이용하도록 한다.

### 핵심 기능

- 카카오 로그인
- 사용자 계정
- 선택 조건 저장
- 프로필 저장
- 북마크
- 북마크 목록
- 최근 본 정책 또는 관심 정책 관리
- 다음 접속 시 저장된 조건 자동 적용

### 로그인 유도 시점

처음부터 로그인시키지 않는다.

예:

```text
정책을 북마크하시겠어요?
→ 로그인

입력한 조건을 다음에도 사용하시겠어요?
→ 로그인
```

### 검증

- 비로그인 사용자 중 실제 로그인 전환 비율
- 북마크 사용률
- 재방문율

---

## MVP 4 — 리텐션 기능

### 목표

찾은 지원 정책을 실제 신청 시점까지 놓치지 않도록 돕는다.

### 핵심 기능

- D-Day
- 신청 일정
- 캘린더
- 마감 알림
- 신청 시작 알림
- 새 정책 알림
- 북마크 정책 변경 알림
- 사용자별 알림 설정

### 사용자 가치

서비스 역할이

> "지원 정책 찾기"

에서

> "지원 정책을 계속 관리해주는 도구"

로 확장된다.

## MVP 4 이후 — 정책 정리 자동화

서비스와 정책 수가 충분히 커졌을 때 진행한다.

- LLM 정책 구조화
- 작업 큐
- 자동 파싱
- 실패 작업 재처리
- 운영자 검수 대기열
- 첨부 PDF/HWP 분석
- 중복 정책 탐지
- 여러 데이터 소스 통합
- 충분한 정확도 검증 후 제한적 자동 공개

LLM이 판단한 결과를 바로 사용자에게 공개하지 않는 것을 기본 원칙으로 한다.

## 8. MVP 우선순위

전체 우선순위는 다음과 같다.

```text
실제 정책 확보
↓
비로그인 정책 탐색
↓
선택형 매칭
↓
정책 수집 자동화
↓
로그인과 개인화
↓
알림과 일정 관리
↓
LLM 운영 자동화
```

초기 핵심은 로그인이나 자동화가 아니라:

> 실제 정책 데이터를 이용해 사용자가 원하는 혜택을 빠르게 찾을 수 있는가?

를 확인하는 것이다.

---

## 9. 초기 성공 기준

### MVP 0

- 실제 정책 30~50건 확보
- 공식 출처 연결 100%
- 주요 조건 데이터 입력 완료

### MVP 1

가장 중요한 성공 기준이다.

- 로그인 없이 바로 정책 탐색 가능
- 조건 입력 후 결과가 정상적으로 좁혀짐
- 테스트 사용자가 실제 자신에게 맞는 정책을 찾을 수 있음
- 명백히 자격이 안 되는 정책을 잘못 추천하는 비율 최소화
- 사용자가 첫 결과를 보기까지 1분 이내를 목표

### MVP 2 이후

운영 효율, 재방문, 로그인 전환, 북마크, 알림 반응 등을 단계별로 측정한다.

초기에는 브라우저 기반 웹 페이지를 기준으로 개발한다.

우선순위:

1. PC 웹

## 11. 하지 않는 것

## 12. 제품의 최종 방향

청년꿀통은 단순 정책 목록 사이트에서 시작한다.

