# 청년꿀통 — AI 에이전트 작업 규칙

> 위치: `docs/AGENT_RULES.md`  
> 목적: 기능을 빠르게 만들되, 사용자가 직접 읽고 이해하고 수정할 수 있는 코드베이스를 유지한다.  
> 기준: **단순성 / 단계적 구현 / 현재 필요한 안전성 / 이해 가능한 코드 / 검증 후 다음 단계**

---

# 1. 문서 구조와 기준

현재 문서 구조는 다음을 기준으로 한다.

```text
docs/
├─ AGENT_RULES.md
├─ ARCHITECTURE.md
├─ PRD.md
├─ mvp-0/
│  ├─ PLAN.md
│  ├─ SPEC.md
│  ├─ SPEC_SUMMARY.md
│  └─ SUMMARY.md
└─ mvp-1/
   ├─ PLAN.md
   ├─ SPEC.md
   ├─ SPEC_SUMMARY.md
   └─ SUMMARY.md
```

MVP 번호가 늘어나면 동일하게 `docs/mvp-{번호}/` 형태를 사용한다.

### 문서 역할

- `docs/PRD.md`: 제품 목적, MVP 범위, 우선순위
- `docs/ARCHITECTURE.md`: 기술 스택, 시스템 구조, DB/API 방향
- `docs/AGENT_RULES.md`: 모든 구현 세션에 공통 적용하는 작업 규칙
- `docs/mvp-N/SPEC.md`: 해당 MVP의 실제 기능 요구사항과 동작 기준
- `docs/mvp-N/PLAN.md`: 구현 Step과 순서
- `docs/mvp-N/SUMMARY.md`: 실제 구현 결과와 현재 상태
- `docs/mvp-N/SPEC_SUMMARY.md`: 사용자가 빠르게 검수하기 위한 요약본

**구현의 최종 기준은 `SPEC.md`이며 `SPEC_SUMMARY.md`는 구현 기준 문서가 아니다.**

---

# 2. 사용자의 실행 명령은 짧게 받는다

사용자는 매 세션마다 긴 프롬프트를 반복하지 않는다.

기본 실행 명령:

```text
MVP 1 Step 3 진행해.
```

에이전트는 MVP 번호와 Step 번호를 기준으로 필요한 문서를 스스로 찾아 진행한다.

추가 요구가 있을 때만 짧게 붙인다.

예:

```text
MVP 1 Step 3 진행해.
이번에는 코드 수정 전에 설계만 먼저 보고해.
```

---

# 3. Step 실행 시 문서 확인 순서

예를 들어 사용자가 `MVP 1 Step 3 진행해.`라고 하면:

## 필수

1. `docs/AGENT_RULES.md`
2. `docs/mvp-1/PLAN.md`의 **Step 3**
3. `docs/mvp-1/SPEC.md`에서 Step 3과 직접 관련된 요구사항
4. `docs/mvp-1/SUMMARY.md`에서 이전 Step까지 실제 구현 상태
5. 현재 Step과 직접 관련된 기존 코드

## 필요할 때만 추가 확인

6. `docs/ARCHITECTURE.md`의 관련 구간
7. `docs/PRD.md`의 관련 구간
8. 이전 MVP의 `SUMMARY.md`

모든 문서를 매번 처음부터 끝까지 읽지 않는다.

`SPEC_SUMMARY.md`는 사용자 검수용이며 구현 판단의 최종 근거로 사용하지 않는다.

---

# 4. 작업 시작 전 확인

현재 Step 구현 전에 다음을 확인한다.

- 이미 완료된 Step인가?
- PLAN과 실제 코드가 일치하는가?
- SPEC과 실제 구현이 충돌하는가?
- 현재 Step 범위를 넘어서는 구조 변경이 필요한가?

이미 완료된 Step이면:

```text
코드 수정 금지
→ 완료 상태와 근거만 보고
→ 종료
```

문서와 코드가 충돌하면 임의 수정하지 않고 먼저 보고한다.

---

# 5. 작업 범위

1. 현재 요청받은 **Step 하나만** 구현한다.
2. 다음 Step, 다음 MVP 기능을 선행 구현하지 않는다.
3. PLAN에 명시되지 않은 구조 변경이 필요하면 먼저 보고하고 승인받는다.
4. SPEC/ARCHITECTURE와 코드가 충돌하면 임의로 문서를 고치지 않는다.

### 별도 승인 필요

현재 Step PLAN에 이미 명시되지 않은 아래 작업은 먼저 보고한다.

- 새로운 외부 패키지 추가
- DB migration 또는 schema 변경
- 폴더/모듈 구조 변경
- 기존 public API 계약 변경
- 공용 type/schema의 호환성을 깨는 변경
- 여러 production 파일을 추가하는 큰 구조 변경
- 파일 삭제, DB 초기화 등 파괴적 작업

현재 Step PLAN에 이미 명시되어 있고 사용자가 Step 진행을 승인했다면 같은 내용을 다시 승인받지 않는다.

---

# 6. 구현 우선순위

```text
정확한 동작
→ 이해하기 쉬운 코드
→ 테스트 가능성
→ 현재 필요한 보안/성능/데이터 무결성
→ 미래 확장성
```

미래 확장성을 이유로 현재 코드를 불필요하게 복잡하게 만들지 않는다.

---

# 7. 단순성 규칙

- 가장 단순하고 직접적인 구현을 우선한다.
- 현재 요구사항에 필요하지 않은 미래 코드를 만들지 않는다.
- 실제 중복이 생기기 전까지 `BaseRepository`, `BaseService`, generic abstraction을 만들지 않는다.
- 구현체가 하나뿐이면 불필요한 Interface / Abstract Class / Factory를 만들지 않는다.
- Helper를 너무 많이 쪼개 코드 흐름을 여러 파일에 분산시키지 않는다.
- 함수가 여러 책임을 가져 읽기 어려울 때만 의미 단위로 나눈다.
- Repository는 DB 접근에 집중한다.
- Service는 비즈니스 규칙과 사용 흐름을 담당한다.
- 순수 계산 로직은 가능하면 DB/NestJS와 분리한다.
- 한 Step에서 사용자가 핵심적으로 읽어야 할 production 파일은 가능하면 2~4개 수준을 목표로 한다.

---

# 8. 주석과 설명

모든 주석과 설명은 한글로 작성한다.

다음에는 짧은 JSDoc 또는 설명 주석을 작성한다.

- 도메인 의미가 있는 type/interface
- 의미를 코드만 보고 이해하기 어려운 Zod Schema
- Service의 주요 public method
- 핵심 비즈니스 로직
- rollback, UNKNOWN 처리 등 구현 이유가 중요한 부분

주석은 가능하면 **왜 이렇게 처리하는지** 설명한다.

좋은 예:

```ts
/**
 * UNKNOWN은 자격 미달이 아니므로 검색 결과에서 제거하지 않는다.
 */
```

불필요한 예:

```ts
// 정책을 저장한다.
repository.save(policy);
```

---

# 9. 현재 필요한 안전성은 지금 구현한다

"단순 구현"은 안전성이나 품질을 무시한다는 뜻이 아니다.

현재 기능에 직접 필요한 것은 즉시 구현한다.

- 입력 검증
- DB 무결성
- 필요한 접근 제어
- 민감정보 로그 방지
- CORS
- 기본 보안 헤더
- public API rate limit
- ORM parameter binding
- 필요한 transaction
- 현재 조회 조건에 필요한 index
- 명확한 오류 응답

---

# 10. 미래 위험은 선행 구현하지 않고 보고한다

아직 실제로 발생하지 않은 문제 때문에 복잡한 구조를 미리 넣지 않는다.

예:

```text
Redis cache
BullMQ
분산락
CQRS
Event Bus
Vector DB
과도한 Repository 추상화
대규모 keyset pagination
```

향후 위험이 보이면 완료 보고에 기록한다.

예:

```text
향후 위험:
- 정책 10,000건 이상에서는 메모리 매칭이 느려질 수 있음
- 현재 MVP 규모에서는 문제 없음
- p95 기준 초과 시 DB filtering/cache 검토
```

원칙:

```text
현재 필요한 문제 → 지금 해결
미래 가능성 → 보고만 함
실제 요구/측정 발생 → 그때 고도화
```

고도화를 프로젝트 마지막에 몰아 하지 않는다. 실제 문제가 확인될 때 필요한 부분만 점진적으로 개선한다.

---

# 11. 예외 처리와 재시도

- 외부 API, DB, 파일 I/O 등 실패 가능한 영역은 오류를 명확히 처리한다.
- 재시도는 **일시적 오류이며 재실행이 안전한 작업**에만 사용한다.
- validation 오류, 잘못된 입력, 권한 오류, 존재하지 않는 데이터는 재시도하지 않는다.
- DB write나 외부 요청을 이유 없이 자동 재시도하지 않는다.
- 오류를 catch한 뒤 조용히 무시하지 않는다.

---

# 12. 성능

- SPEC에 명시된 현재 성능 기준은 만족해야 한다.
- 실제 측정 없이 캐시나 복잡한 최적화를 추가하지 않는다.
- N+1처럼 명확한 문제는 현재 단계에서 방지한다.
- index는 실제 조회 조건에 필요한 범위만 추가한다.
- 현재 규모에서 문제가 없다면 미래 최적화는 보고만 한다.

---

# 13. 테스트

주요 기능 추가/수정 시 관련 테스트를 작성하거나 보강한다.

```text
순수 비즈니스 로직 → Unit Test
DB/API 경계 → Integration Test
핵심 사용자 흐름 → E2E
```

- 현재 Step 테스트가 통과한 뒤 종료한다.
- 테스트를 통과시키기 위해 요구사항을 임의 변경하지 않는다.
- 사용자가 직접 확인할 명령 또는 브라우저 확인 방법도 제공한다.

---

# 14. 보안 / 개인정보

- API Key, DB 비밀번호, Token을 하드코딩하지 않는다.
- 환경변수를 사용한다.
- 로그에 비밀번호, Token, Cookie 전체, 소득, 생년월일, 민감한 전체 request body를 남기지 않는다.
- 민감한 검색 조건은 URL query보다 request body를 우선한다.

---

# 15. PLAN / SUMMARY 갱신

Step 완료 후:

1. `docs/mvp-N/PLAN.md`의 현재 Step 체크 항목만 `[x]`로 갱신한다.
2. `docs/mvp-N/SUMMARY.md`에 실제 구현 결과를 핵심적으로 추가한다.
3. PRD / ARCHITECTURE / SPEC의 의미를 임의 변경하지 않는다.
4. 설계 변경은 사용자 승인 후 문서에 반영한다.
5. 새로운 문서를 임의로 추가하지 않는다.

---

# 16. Git

- Git commit은 직접 실행하지 않는다.
- 완료 후 논리적인 commit 단위와 한글 commit message를 제안한다.

예:

```text
feat: 정책 목록 조회 API 구현
test: 정책 목록 조회 통합 테스트 추가
```

---

# 17. Step 완료 보고 형식

```text
구현 내용:
- ...

변경 파일:
- ...

API / DB 변경:
- ...

테스트:
- 명령:
- 결과:

코드를 읽을 추천 순서:
1. ...
2. ...
3. ...

새로 등장한 주요 개념:
- ...

향후 위험 / 아직 구현하지 않은 것:
- ...

추천 commit:
1. feat: ...
2. test: ...
```

보고 후 반드시 중단한다.

다음 Step은 사용자의 다음 요청 후 진행한다.

---

# 18. 최종 사용 방식

앞으로 사용자는 다음 정도만 입력하면 된다.

```text
MVP 1 Step 3 진행해.
```

별도 `STEP_PROMPT.md`는 필요하지 않다.
