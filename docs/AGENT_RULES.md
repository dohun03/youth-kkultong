# 청년꿀통(youth-kkultong) — AI 에이전트 작업 규칙

> 위치: `docs/AGENT_RULES.md`  
> 목적: 사용자가 직접 이해하고 수정할 수 있는 코드로 MVP를 단계적으로 완성한다.  
> 원칙: **요구사항 준수 · 단순한 구조 · 현재 필요한 안정성 · 검증 후 완료 · 문서와 구현의 일치**

## 1. 문서 구조와 역할

```text
docs/
├─ AGENT_RULES.md
├─ ARCHITECTURE.md
├─ PRD.md
├─ mvp-1/
│  ├─ PLAN.md
│  ├─ SPEC.md
│  ├─ SPEC_SUMMARY.md
│  └─ SUMMARY.md
└─ mvp-2/
   ├─ PLAN.md
   ├─ SPEC.md
   ├─ SPEC_SUMMARY.md
   └─ SUMMARY.md
```

MVP가 추가되면 `docs/mvp-N/` 형식을 따른다.

| 문서 | 역할 |
| --- | --- |
| `PRD.md` | 제품 목표, MVP 범위, 사용자 기능과 정책 |
| `ARCHITECTURE.md` | 공통 기술 스택, 시스템 구성, 모듈 경계, 데이터 흐름 |
| `mvp-N/SPEC.md` | 해당 MVP의 DB·API·타입·기능 동작·예외·테스트 기준 |
| `mvp-N/PLAN.md` | Step별 작업 범위, 순서, 완료 조건 |
| `mvp-N/SUMMARY.md` | 실제 구현 결과, 검증 내용, 다음 작업을 위한 상태 |
| `mvp-N/SPEC_SUMMARY.md` | 사용자가 빠르게 검수하는 요약본 |
| `AGENT_RULES.md` | 모든 세션에 적용하는 공통 작업 규칙 |

**구현 세부 기준은 `SPEC.md`이며, `SPEC_SUMMARY.md`는 구현 근거로 사용하지 않는다.** 문서 사이에 충돌이 있으면 임의로 우선순위를 정해 구현하지 않고 충돌 내용과 해결안을 보고한다.

## 2. Step 실행 방식

사용자는 다음과 같이 간단히 요청한다.

```text
MVP 1 Step 3 진행해.
```

에이전트는 요청된 Step 하나만 진행한다. 확인 순서는 다음과 같다.

1. `AGENT_RULES.md`
2. 해당 MVP의 `PLAN.md`에서 요청된 Step
3. `SPEC.md`의 관련 요구사항
4. `SUMMARY.md`의 실제 완료 상태
5. 관련 소스코드
6. 구조·제품 정책 판단이 필요할 때만 `ARCHITECTURE.md`, `PRD.md` 및 이전 MVP 기록

관련 없는 문서 전체를 반복해서 읽지 않는다. 이미 완료된 Step이라면 코드를 다시 수정하지 않고 완료 근거를 보고한다. 사용자 요청이 **문서 검수·수정만**인 경우에는 구현 작업을 진행하지 않는다.

## 3. 착수 전 확인과 승인

작업 전에 **PLAN / SPEC / 실제 코드의 일치 여부, 이전 Step의 완료 여부, 현재 Step의 범위**를 점검한다.

현재 Step에 이미 포함된 작업은 재승인 없이 진행한다. 아래와 같이 **승인된 범위를 실질적으로 바꾸는 작업**은 변경 사유·대안·영향 파일을 간단히 보고하고 승인을 받은 뒤 진행한다.

- MVP 기능·판정 규칙·API 계약 변경
- DB 스키마·Migration(스키마 변경 기록)의 계획 외 수정
- 모듈·폴더 경계 변경 또는 새로운 서비스·인프라 도입
- 계획에 없는 외부 패키지 도입
- 기존 데이터 삭제·초기화 또는 사용자 작업물에 영향을 줄 수 있는 변경

코드에서 작은 오류를 바로잡거나 기존 명세를 그대로 구현하기 위한 내부 수정은 현재 Step 범위에서 처리한다. 예상과 다른 설계 문제가 생기면 무리하게 우회 구현하지 않고 먼저 보고한다.

## 4. 설계 변경 시 문서 동기화

**문서는 최초 계획이 아니라 실제 합의된 설계와 구현 상태를 나타내야 한다.**

- 기존 문서대로 구현하기 어려우면 먼저 이유와 대안을 보고한다. **설계·기능의 의미가 달라지는 변경은 승인 후** 관련 문서를 수정하고 구현한다.
- 승인된 변경은 영향받는 문서에 함께 반영한다. 제품 범위는 `PRD`, 공통 구조는 `ARCHITECTURE`, 기능·DB·API 규칙은 해당 `SPEC`, 작업 순서는 `PLAN`에서 수정한다.
- 단순 오탈자·설명 누락·실제 구현과 같은 의미로 표현하는 정정은 직접 반영하되, 완료 보고에 변경 사실을 남긴다.
- 실제 구현 중 결정된 세부 사항과 검증 결과는 `SUMMARY`에 기록한다. 미완료 작업은 완료로 표시하지 않는다.
- 관련 없는 장을 전면 재작성하거나 문서를 새로 늘리지 않는다. 같은 규칙을 여러 문서에 상세히 반복하기보다 **소관 문서 한곳에 정의하고 다른 문서에서 참조**한다.

문서 변경만으로 코드가 자동으로 올바르게 바뀐 것으로 간주하지 않는다. 변경한 요구사항은 관련 테스트와 실제 코드까지 확인한다.

## 5. 구현 원칙

우선순위: **정확한 동작 → 이해하기 쉬운 코드 → 테스트 가능성 → 필요한 안전성·성능 → 확장성**.

- 현재 Step의 핵심 기능을 가장 단순하고 직관적인 방식으로 구현한다.
- 실제 필요가 확인되기 전에는 `BaseService`, `BaseRepository`, Factory(생성 전담 구조), 과도한 Interface(인터페이스)·추상 계층을 추가하지 않는다.
- 코드 재사용성이나 책임 분리가 분명할 때 메서드·파일을 분리한다. 한 번만 쓰는 짧은 로직을 지나치게 쪼개지 않는다.
- Repository(저장소 계층)는 DB 접근, Service(서비스 계층)는 업무 흐름, 순수 함수는 계산·판정에 집중한다.
- 엔티티(Entity, DB 저장 모델)는 소속 모듈에서 관리하고, 프런트·백엔드 공용 타입에는 API 계약을 둔다.
- 가능하면 한 Step에서 핵심적으로 읽을 코드 파일 수를 적게 유지한다. 단, 책임을 억지로 한 파일에 몰아넣지는 않는다.
- 이미 작성된 정상 동작이나 사용자 변경사항을 불필요하게 덮어쓰지 않는다.

## 6. MVP1 아키텍처 준수

현재 MVP1의 기술·구조 기준은 `ARCHITECTURE.md`, 세부 처리 방식은 `mvp-1/SPEC.md`를 따른다.

- 기반: **Next.js · NestJS · PostgreSQL · TypeORM · Zod · Docker Compose**.
- `Policies`는 정책 조회·저장, `Ingestion`은 외부 API 수집·검증, `Matching`은 매칭·점수, `Meta`는 선택 항목 제공을 담당한다.
- 수집 중복 실행에는 설계에 정해진 **PostgreSQL Advisory Lock(중복 실행 잠금)** 을 사용한다.
- 수집의 재시도 대상·횟수, 변환 검증, 묶음 저장 및 전체 트랜잭션 처리 기준은 SPEC에 따른다. 모든 종료 경로에서 오류 기록·자원 정리를 확인한다.
- 이후 기능을 위한 Redis, BullMQ, 분산 작업 처리, 캐시, 별도 Worker 등은 실제 필요와 승인된 설계에 따라 도입한다.

이 장은 **기술 선택의 요약**이며, API 경로나 수치·세부 규칙을 별도로 중복 정의하지 않는다.

## 7. 예외 처리·데이터 안전성

- 외부 API, DB, 파일 작업은 실패 가능성을 고려하고 오류의 발생 단계·원인을 확인할 수 있게 기록한다.
- 재시도는 **일시적이고 재실행이 안전한 오류**에 한정한다. 구조 검증 실패, 잘못된 입력, 권한 오류 등을 반복 재시도하지 않는다.
- 트랜잭션 실패 시 롤백하고, `finally` 등으로 잠금·연결을 안전하게 정리한다. 오류 로그 자체가 실패해도 자원 정리를 계속 시도한다.
- 사용자 입력은 Zod 등 명세에 맞게 검증하고, DB 제약조건·중복 방지·필요한 인덱스를 구현한다.
- 예외를 잡은 뒤 조용히 무시하거나 임의의 정상값으로 바꿔 성공 처리하지 않는다.

## 8. 성능과 테스트

- 현재 데이터 규모와 SPEC의 성능·정확성 기준을 우선한다. 측정 없이 캐시·복잡한 최적화를 선행하지 않는다.
- N+1 조회 등 명백한 낭비는 현재 Step에서 예방한다. 나중에 필요할 고도화는 `SUMMARY`의 개선 과제로 기록한다.
- 변경한 규칙에는 관련 테스트를 추가·보강한다: 순수 계산은 Unit Test(단위 테스트), DB·API는 Integration Test(통합 테스트), 주요 사용자 흐름은 필요 시 E2E(전체 흐름 테스트).
- 실행 가능한 테스트를 실제 수행하고 결과를 보고한다. 환경 제약으로 실행하지 못했으면 **미실행 사유**를 명시한다.
- 테스트 통과를 위해 요구사항을 임의로 낮추거나 변경하지 않는다.

## 9. 보안·개인정보

- API 키·비밀번호·토큰은 환경변수로 관리하고 코드·Git·로그에 노출하지 않는다.
- 사용자 조건 및 민감한 요청 본문을 DB나 로그에 불필요하게 저장하지 않는다.
- 공개 API에는 입력 검증, 필요한 접근 제어·호출 제한, CORS(출처 간 요청 제한), 기본 보안 헤더를 적용한다.
- DB 접근은 ORM의 매개변수 바인딩을 활용하고, 파괴적 명령은 사용자 승인 범위에서만 실행한다.

## 10. 주석·문서 작성 방식

- **설명·주석·보고는 한국어**로 작성한다. 코드 식별자와 기술 표준 명칭은 관례를 따른다.
- 영어 개발 용어가 이해를 방해할 때는 처음 등장하는 위치에 한국어 뜻을 함께 쓴다.
- 타입, 인터페이스, 메서드, 함수 등의 상단이나 핵심 로직에는 **해당 요소의 명확하고 간결한 역할**을 주석이나 JSDoc으로 작성한다.
- 모호하거나 장황한 설명 대신, 무엇을 하는지 직관적으로 알 수 있는 실용적인 표현을 사용한다. (예: "공통 에러 규격 함수", "날짜 변환 함수", "특정 테이블 데이터 저장 함수", "트랜잭션 활성화", "DB 락 획득")
- 코드만 봐도 명확한 내용을 줄마다 해설하거나 장황한 부연 설명을 중복 작성하지 않는다.
- 문서는 핵심 결정·동작·예외·검증 방법 위주로 작성하며, 현재 수행할 기능을 중심으로 기술한다.

## 11. Step 완료·문서 갱신

1. 현재 Step의 구현·테스트·검증 결과를 확인한다.
2. 완료 조건을 충족한 항목만 `PLAN.md`에서 `[x]`로 표시한다.
3. `SUMMARY.md`에 구현 내용, 실제 결정사항, 남은 문제를 간결하게 기록한다.
4. 승인되거나 필요한 정정으로 변경된 설계를 관련 `PRD`·`ARCHITECTURE`·`SPEC`·`PLAN`에 일관되게 반영한다.
5. `SPEC_SUMMARY.md`가 있다면 사용자 검수에 영향을 줄 만큼 SPEC 내용이 바뀐 경우에만 해당 요약을 맞춘다.

문서와 코드의 불일치가 남아 있으면 이를 명시하고 완료로 보고하지 않는다.

## 12. Git과 완료 보고

Git commit(커밋)은 직접 실행하지 않고 **논리적 커밋 단위와 한국어 메시지**를 제안한다.

완료 보고는 아래 형식으로 짧고 구체적으로 작성한다.

```text
구현 내용:
- ...

변경 파일:
- ...

API / DB / 문서 변경:
- ...

검증:
- 실행 명령:
- 결과: 통과 / 실패 / 미실행(이유)

핵심 코드 읽는 순서:
1. ...
2. ...

남은 문제 또는 후속 검토:
- ...

추천 커밋:
- feat: ...
```

**보고 후 중단한다.** 다음 Step은 사용자가 별도로 요청할 때 진행한다.
