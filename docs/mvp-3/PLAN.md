## 1. 진행 원칙

- Step 하나를 기본 커밋 단위로 삼는다. 제품 소스는 보통 3~6개 파일 안에서 한 책임을 다루고, 관련 테스트와 결과 문서를 함께 갱신한다. 독립된 업무가 섞이거나 수정 범위가 커지면 책임별로 더 나눠 진행한다.
- 기능마다 백엔드와 테스트를 준비한 뒤 해당 화면까지 연결한다. 각 단계가 끝나면 목록 탐색, 일괄 검수, 수집 조회, 웹 수집을 차례로 직접 사용할 수 있어야 한다.
- 타입과 내부 함수를 먼저 준비하는 Step은 전체 타입 검사와 기존 동작을 유지한다. 새 계약은 이를 처리할 서비스와 컨트롤러를 연결하는 Step에서 적용한다.
- 변경한 동작의 테스트는 해당 Step에서 수행한다. 최종 회귀는 그동안의 통합 결과를 확인하는 단계다.
- API와 DB 검증은 격리된 PostgreSQL, 화면 검증은 실제 API 연결을 기본으로 한다. 실패 주입과 모의 외부 응답의 검증 범위를 실제 온통청년 호출과 구분해 기록한다.
- 화면 변경 Step은 검증 후 AGENT_RULES에 따라 최신 웹 빌드로 확인할 수 있게 반영한다. 필요한 API와 DB 변경도 해당 개발 환경에 맞춘다.
- 완료한 Step만 체크하고 `SUMMARY.md`에 구현, 검증과 남은 문제를 기록한다. SUMMARY는 Step 1에서 실제 시작 상태로 작성한다. 각 Step 종료 시 한국어 커밋 메시지를 제안하고 사용자 요청에 따라 다음 Step을 진행한다.

아래 주요 위치는 작업의 중심 파일이나 폴더다. 백엔드 경로는 `apps/api/src/modules/`, 웹은 `apps/web/app/admin/`, shared는 `packages/shared/src/`를 기준으로 읽는다. 여러 Step에 걸친 검증 번호는 각 Step의 변경 범위를 확인한다. Step 32에서 전체 회귀와 검증 대응표를 정리하고, Step 34의 복원 및 전환 검증까지 마친 뒤 Step 35에서 전체 시나리오의 최종 충족 여부를 판정한다.

## 2. 전체 개발 순서

| 단계 | Step | 진행 흐름 | 단계 완료 시 사용할 기능 |
| --- | --- | --- | --- |
| A. 시작 상태 | 1 | 기준 문서와 기존 구현 확인 | 작업 기준과 검증 환경 |
| B. 검수 목록 | 2~7 | 중요도 계산 → 목록 API → 화면과 상태 복원 | 중요도 기준으로 대기열 탐색 |
| C. 일괄 검수 | 8~16 | 입력과 안전장치 → 처리 API → 선택, 확인과 결과 화면 | 현재 페이지의 일괄 승인과 거절 |
| D. 수집 조회 | 17~28 | 실행 DB → CLI/Cron 기록 → 조회 API → 상태와 이력 화면 | 실제 수집 상태와 과거 결과 조회 |
| E. 웹 수집 | 29~31 | 비동기 접수 API → 실행 버튼 → 동시 실행 검증 | 웹에서 수집 시작과 결과 확인 |
| F. 최종 인수 | 32~35 | 전체 회귀 → 복원과 전환 재현 → 대상 환경 적용 | 운영 가능한 MVP3 |

수집 조회 단계에서는 CLI와 Cron이 만든 실행 기록으로 화면을 연결한다. 웹 수집 단계는 이 흐름에 관리자 실행 요청을 추가한다.

## 4. B. 중요도와 검수 목록 — Step 2~7

### Step 2. 변경 중요도 계산 함수

**설명:** 어떤 원본 필드가 바뀌었는지 보고 리뷰의 중요도를 계산한다.

- [ ] 분류 공용 타입과 60개 필드 매핑을 정의하고 기존 필드 차이 함수와 연결한다.
- [ ] 혼합 변경, 미분류 필드, 신규, 조회수와 손상된 스냅샷을 단위 테스트한다.

**주요 위치:** `policies/rules/reviews/policy-review-importance.ts`, shared `admin.ts`.
**완료 조건:** 같은 스냅샷에는 같은 분류가 나오고 미분류와 경고 정보를 함께 반환한다.
**SPEC 참조:** 2장, 7.2절. **검증:** T3-01~06.

### Step 3. 전체 대기 후보 조회와 정렬

**설명:** 조건에 맞는 후보 전체를 가져와 중요도를 계산하고 마지막에 페이지를 나눈다.

- [ ] Repository에 대기 메타정보와 스냅샷의 일괄 조회를 준비하고 기존 제목 검색 조건을 재사용한다.
- [ ] 읽기 서비스에서 중요도 필터, 세 정렬, total과 페이지를 계산하고 다음 API 연결에서 사용할 결과를 검증한다.

**주요 위치:** `policies/repositories/policy-review.repository.ts`, `policies/services/reviews/policy-reviews-read.service.ts`.
**완료 조건:** 뒤쪽 후보까지 포함해 필터와 정렬이 적용되고 건수와 페이지 항목이 같은 조회 결과에서 나온다.
**SPEC 참조:** 3.2절. **검증:** T3-09~11.

### Step 4. 검수 조회 API와 계약 연결

**설명:** 화면이 중요도와 정렬 조건을 보내고 분류 결과를 받을 수 있게 한다.

- [ ] 대기 조회의 query 타입과 Zod 검증을 서비스에 연결하고 목록, 상세와 이력에 분류 요약을 제공한다.
- [ ] 필터 조합과 페이지 개수를 검증하고 기존 이력, 누락, 공개 API 계약의 유지 범위를 확인한다.

**주요 위치:** shared `admin.ts`, `admin.schema.ts`, 검수 읽기 서비스와 관리자 컨트롤러.
**완료 조건:** 실제 HTTP 요청으로 필터와 분류를 확인할 수 있고 목록과 상세의 분류가 일치한다.
**SPEC 참조:** 2.3절, 3.1절, 7.1절. **검증:** T3-07~08, T3-12.

### Step 5. 중요도 표시와 목록 조작 화면

**설명:** 관리자가 중요도를 보고 필터와 정렬을 직접 선택할 수 있게 한다.

- [ ] 대기 목록에 유형과 중요도 필터, 정렬, 표시 개수와 대기 기간을 연결한다.
- [ ] 상세에 중요도, 미분류 필드와 경고를 표시하고 로딩, 빈 결과, 오류와 초과 페이지 복구를 확인한다.

**주요 위치:** 웹 `reviews/page.tsx`, `reviews/[id]/`, `admin.css`.
**완료 조건:** 실제 API의 전체 건수와 정렬이 화면에 일치하고 신규 선택 시 중요도 조건이 정리된다.
**SPEC 참조:** 3장, 8.1절. **검증:** T3-07~12, T3-15.

### Step 6. 검수 목록의 탐색 상태 복원과 인증 재확인

**설명:** 상세를 보고 돌아오거나 새로고침해도 방금 보던 목록 위치를 되찾게 한다.

- [ ] 적용된 검색어, 필터, 정렬, 개수와 현재 페이지를 sessionStorage에 저장하고 첫 조회 전에 복원한다.
- [ ] 저장값 손상, 저장소 접근 실패, 필터 조합 정리와 인증 종료 시 삭제를 검증한다.
- [ ] 공통 인증에서 최초 확인과 로그인 후 백그라운드 재확인을 구분한다. 탭 복귀와 재확인 오류는 기존 화면을 unmount하지 않고, 만료 또는 로그아웃 확인 시 보호 화면과 메모리를 제거한다.

**주요 위치:** 웹 `reviews/`의 상태 관리, `admin-session.tsx`.
**완료 조건:** 상세 복귀와 새로고침에서 같은 탐색 조건이 복원되고 저장소 오류가 화면 사용을 막지 않는다. 최초 인증 보호와 재확인 중 화면 상태 보존을 함께 검증한다.
**SPEC 참조:** 8장 공통 인증, 8.1절. **검증:** T3-14~15, T3-44의 공통 인증 동작.

### Step 7. 검수 목록 기능 인수

**설명:** 많은 후보가 있어도 목록과 상세를 정확하게 탐색할 수 있는지 확인한다.

- [ ] SPEC의 데이터 규모로 목록 응답 시간, 조회 횟수와 메모리 사용을 측정한다.
- [ ] 실제 API와 브라우저에서 중요도 검색, 정렬, 페이지 이동과 복원, 인증 및 좁은 화면을 검수한다.

**주요 위치:** 목록 API 통합 테스트, 검수 목록과 상세 브라우저 테스트.
**완료 조건:** 목록 성능 기준과 핵심 탐색 흐름을 충족하고 기존 이력과 누락 조회도 유지된다.
**SPEC 참조:** 3.2절, 8.1절. **검증:** T3-07~15.

## 5. C. 일괄 검수 — Step 8~16

### Step 8. 일괄 검수 입력과 결과 타입

**설명:** 여러 리뷰의 처리 요청과 항목별 결과를 주고받는 형식을 준비한다.

- [ ] 일괄 승인, 거절과 상태 재조회 타입 및 Zod 스키마를 정의한다.
- [ ] 개수, 정규화한 UUID의 중복, 두 해시, 공통 사유와 알 수 없는 입력 필드를 검증한다.

**주요 위치:** shared `admin.ts`, `admin.schema.ts`, `index.ts`.
**완료 조건:** 잘못된 항목 하나도 요청 검증에서 식별되며 결과 타입이 성공, 충돌, 실패와 확인 불가를 표현한다.
**SPEC 참조:** 4.1절, 7.2절. **검증:** T3-18.

### Step 9. 일괄 API의 본문 한도

**설명:** 리뷰 100건의 ID와 해시를 보내도 본문 크기 제한 때문에 막히지 않게 한다.

- [ ] 일괄 처리와 상태 재조회 경로에 SPEC의 본문 한도를 적용한다.
- [ ] 나머지 경로의 한도, 압축 거부, 실제 수신 크기 검사와 라우터 경로 처리를 확인한다.

**주요 위치:** `apps/api/src/main.ts`, `apps/api/src/common/request-protection.ts`, 요청 보호 통합 테스트.
**완료 조건:** 큰 일괄 본문을 받을 준비가 되고 공개 API와 인증 API의 제한은 유지된다.
**SPEC 참조:** 7.3절. **검증:** T3-26.

### Step 10. 개별 검수 서비스의 실행 결과 구분

**설명:** 저장이 취소된 경우와 저장됐는지 모르는 경우를 구분할 수 있게 한다.

- [ ] 기존 승인과 거절 서비스에 일괄 호출용 SQL 및 DB 응답과 연결 정리 제한, 실행 단계별 내부 오류 정보를 연결한다.
- [ ] 롤백 확정, COMMIT 응답 유실과 무응답, 연결 폐기, 확정 후 정리 실패와 기존 재시도를 검증한다. 단순 시간 초과를 미반영으로 판정하거나 늦은 흐름이 COMMIT하지 않게 한다.

**주요 위치:** `policies/services/reviews/policy-review-approval.service.ts`, `policy-review-rejection.service.ts`와 관련 내부 타입.
**완료 조건:** 일괄 처리에서 반영 여부를 구분할 수 있으며 기존 개별 HTTP 검수 계약과 잠금 순서를 유지한다.
**SPEC 참조:** 4.2절, 6.6절. **검증:** T3-19~20, T3-23~24.

### Step 11. 후보별 일괄 처리 서비스

**설명:** 선택한 리뷰를 하나씩 처리하고 각 결과를 모아 돌려준다.

- [ ] `PolicyReviewsBatchService`에서 기존 승인 또는 거절 서비스를 순서대로 호출하고 항목별 결과와 집계를 조립한다.
- [ ] 공통 사유 저장, 부분 성공, 오류 이후 다음 후보 처리와 결과 순서를 검증한다.

**주요 위치:** `policies/services/reviews/policy-reviews-batch.service.ts`, `policies.module.ts`.
**완료 조건:** 한 후보의 실패가 이미 성공한 후보를 취소하지 않고 집계 합계가 요청 건수와 일치한다.
**SPEC 참조:** 4.1~4.2절. **검증:** T3-19~21, T3-23~24.

### Step 12. 일괄 검수와 상태 재조회 API

**설명:** 화면이 일괄 처리를 요청하고 응답을 잃었을 때 현재 상태를 확인할 수 있게 한다.

- [ ] 일괄 승인과 거절을 관리자 컨트롤러에 연결하고 상태 재조회용 일괄 SELECT를 추가한다.
- [ ] 인증, Origin, 입력 선검증, 항목별 오류와 현재 상태 응답을 실제 HTTP로 검증한다.

**주요 위치:** 관리자 검수 컨트롤러, 검수 Repository와 읽기 서비스.
**완료 조건:** 세 API가 계약대로 동작하고 거부된 전체 요청은 검수 쓰기를 시작하지 않는다.
**SPEC 참조:** 4.3절, 7.1~7.3절. **검증:** T3-18~21, T3-25~26.

### Step 13. 현재 페이지의 체크박스 선택

**설명:** 관리자가 지금 보고 있는 리뷰 중 처리할 항목을 고르게 한다.

- [ ] 개별 선택, 전체 선택, 일부 선택 표시와 선택 건수를 구현한다.
- [ ] 페이지, 조건, 재조회와 상세 이동에 따른 선택 초기화를 연결한다.

**주요 위치:** 웹 `reviews/page.tsx`와 목록 컴포넌트.
**완료 조건:** 현재 페이지의 후보만 선택되며 탐색 조건의 저장과 체크박스 상태가 섞이지 않는다.
**SPEC 참조:** 8.1절. **검증:** T3-16.

### Step 14. 승인과 거절 확인 및 결과 화면

**설명:** 선택 건수와 거절 영향을 확인한 뒤 실행하고 후보별 결과를 보여준다.

- [ ] 승인 확인과 거절 사유 모달을 연결하고 초점 이동, 취소, 입력 검증과 중복 제출 방지를 적용한다.
- [ ] 실제 일괄 API 결과와 집계를 표시하고 목록 갱신 뒤에도 결과 패널을 유지한다.
- [ ] SPEC 7.3절에 맞춰 브라우저 대기를 기존 프록시와 같은 30초로 두고, 탭 복귀의 인증 재확인 중 진행 대상과 결과 패널을 보존한다.

**주요 위치:** 웹 `reviews/`의 확인 모달과 결과 패널, `admin.css`.
**완료 조건:** 확인을 거친 요청만 제출되고 성공, 충돌, 실패와 확인 필요를 후보별로 구분한다.
**SPEC 참조:** 7.3절, 8장 공통 인증, 8.2절. **검증:** T3-17, T3-19~21, T3-25의 상태 보존.

### Step 15. 응답 유실 후 결과 재확인 화면

**설명:** 처리 응답이 끊겨도 승인 요청을 반복하지 않고 현재 DB 상태를 확인한다.

- [ ] 일괄 응답 유실과 UNKNOWN을 상태 재조회로 연결하고 제한된 자동 조회 및 수동 재조회를 제공한다.
- [ ] 원래 요청 결과와 현재 관측 상태, 아직 대기, 조회 실패와 인증 만료를 구분한다. 브라우저 또는 프록시 연결 종료와 탭 복귀에서 POST를 반복하지 않는다.

**주요 위치:** 웹 `reviews/`의 제출과 결과 재조회 처리.
**완료 조건:** 불명확한 결과를 실패로 단정하지 않으며 이미 처리된 후보를 자동으로 다시 제출하지 않는다.
**SPEC 참조:** 4.3절, 8.2절. **검증:** T3-24~25.

### Step 16. 일괄 검수의 경쟁과 화면 인수

**설명:** 다른 탭의 검수나 수집과 겹쳐도 처리 결과가 안전하게 유지되는지 확인한다.

- [ ] 실제 별도 DB 연결로 일괄과 개별 검수, 승인과 거절, 수집 저장의 경쟁을 재현한다.
- [ ] 실제 Next.js 프로덕션 프록시를 통과하는 화면에서 100건 처리의 30초 전후 응답, 연결 종료 후 서버 처리 지속과 batch-status 재확인을 검수한다. 부분 성공과 탭 복귀의 진행 대상 및 결과 패널 보존도 확인한다.

**주요 위치:** 검수 동시성 통합 테스트, 일괄 검수 브라우저 테스트.
**완료 조건:** 중복 공개와 이력 없이 기존 잠금 규칙을 유지하고 선택부터 결과 확인까지 사용할 수 있다.
**SPEC 참조:** 4장, 8.2절. **검증:** T3-16~26.

## 6. D. 수집 상태와 실행 기록 — Step 17~28

### Step 17. 수집 조회와 접수 계약 준비

**설명:** 수집 상태, 실행 기록과 접수 결과를 화면과 서버가 같은 형식으로 다루게 한다.

- [ ] 수집 공용 타입과 Zod 스키마, 목록 페이지와 requestId 검증을 정의한다.
- [ ] 상태, 반영 여부, NULL 집계와 안전한 오류 형식을 검증한다.

**주요 위치:** shared `admin-ingestion.ts`, `admin-ingestion.schema.ts`, `index.ts`.
**완료 조건:** 실행 결과와 DB 반영 여부를 구분하고 목록, 상세와 현재 상태를 각각 표현한다.
**SPEC 참조:** 7.1~7.3절. **검증:** T3-29~30, T3-43, T3-45, T3-48의 계약 검증.

### Step 18. 실행 요약 테이블과 엔티티

**설명:** 수집이 끝나거나 서버가 재시작돼도 실행 결과를 보관할 DB를 만든다.

- [ ] Ingestion 소유 엔티티와 Migration에 실행 컬럼, 상태별 제약과 조회 인덱스를 구현한다.
- [ ] 격리 DB에 적용해 잘못된 결과 JSON, 시각과 중복 실행을 검증하고 기존 정책과 검수 보존을 확인한다.
- [ ] 검증한 Migration을 DB와 로그 백업 후 개발 DB에 적용해 후속 수집 기능의 실행 기반을 준비한다.

**주요 위치:** `ingestion/entities/ingestion-run.entity.ts`, `apps/api/src/database/migrations/`.
**완료 조건:** 실제 DB 제약과 엔티티가 일치하고 새 테이블만 추가된다.
**SPEC 참조:** 5장. **검증:** T3-27.

### Step 19. 실행 기록 저장소

**설명:** 실행 ID를 기준으로 접수와 단계, 결과를 안전하게 읽고 갱신한다.

- [ ] 접수, 소유 세션 확인, 조건부 상태 갱신과 확정 결과 저장을 Repository에 구현한다.
- [ ] 허용된 이전 상태와 갱신 건수를 확인하고 안전한 오류 정보만 기록하도록 테스트한다.

**주요 위치:** `ingestion/repositories/ingestion-run.repository.ts`, `ingestion.module.ts`.
**완료 조건:** 종료된 실행을 오래된 갱신으로 되돌리지 않고 같은 requestId와 활성 실행 제약을 지킨다.
**SPEC 참조:** 5.2절, 6.1절. **검증:** T3-27, T3-29, T3-42, T3-45.

### Step 20. 수집 저장과 반영 증거 연결점

**설명:** 정책 저장과 실행 결과 기록을 같은 트랜잭션에서 확정할 준비를 한다.

- [ ] `saveCollection`에 SPEC의 선택적 beforeCommit 콜백을 추가하고 재시도에서도 같은 저장 경계를 적용한다.
- [ ] 콜백 오류로 정책 저장 전체가 취소되는지 검증하고 기존 호출의 동작을 유지한다.

**주요 위치:** `policies/services/collection/policy-collection-write.service.ts`, 관련 내부 타입과 저장 통합 테스트.
**완료 조건:** 실행 증거 쓰기를 연결할 수 있고 증거 실패 시 부분 저장이 생기지 않는다.
**SPEC 참조:** 6.3절. **검증:** T3-33~34, T3-36.

### Step 21. 잠금 소유 정보와 종료 연결점

**설명:** 실제로 수집 잠금을 쥔 연결을 식별하고 실행 기록과 정리 절차를 연결한다.

- [ ] 기존 Advisory Lock에서 소유 세션 정보 조회와 실행 종료 처리의 연결점을 준비하고, 연결 확보와 응답 및 정리의 대기 상한과 실패한 연결 폐기를 연결한다.
- [ ] 선택적 연결점 없이도 기존 잠금 획득과 중복 종료가 유지되는지 검증한다. 정리 무응답 시 후속 SQL과 정상 풀 반환을 막고, 실제 잠금 해제는 후속 DB 확인으로 판정한다.

**주요 위치:** `ingestion/services/ingestion-lock.service.ts`, 잠금 단위 및 통합 테스트.
**완료 조건:** 접수부터 종료까지 같은 잠금 연결을 유지할 수 있고 실패 경로에서도 정리를 시도한다.
**SPEC 참조:** 6.2절, 6.4절, 6.6절. **검증:** T3-31~32, T3-37, T3-41.

### Step 22. 실행 종료와 오류 기록

**설명:** DB 반영 결과와 로그 또는 정리 오류를 구분해 실행의 마지막 상태를 남긴다.

- [ ] 실행 서비스에 종료 행 잠금과 자원 정리 순서, 종료 트랜잭션의 SQL 및 전체 대기 상한, 파일과 대체 로그의 대기 상한을 연결한다. 기존 로그의 안전한 오류 변환을 확장한다.
- [ ] 확정 결과 보호, 로그와 DB 무응답, 종료 기록 실패와 새 실행의 경쟁을 실제 DB에서 검증한다. 늦은 응답이나 로그가 종료 상태를 바꾸지 않게 한다.

**주요 위치:** `ingestion/services/ingestion-runs.service.ts`, 실행 저장소와 로그 서비스의 필요한 연결부.
**완료 조건:** DB 반영 후 오류에도 집계를 보존하고 실행 기록 실패가 잠금 정리를 막지 않는다.
**SPEC 참조:** 6.1절, 6.4절, 6.6절. **검증:** T3-35~37, T3-42, T3-45.

### Step 23. 재시작 후 실행 상태 복구

**설명:** 오래된 실행 중 기록이 실제 작업인지 중단된 작업인지 확인한다.

- [ ] 실제 잠금과 PID 및 세션 시작 시각을 대조하고 배타적 잠금 아래에서 미완료 기록을 정리한다.
- [ ] 반영 증거 유무, 남은 UNKNOWN, 별도 CLI 실행과 조회 실패를 검증한다. COMMIT 응답 시간 초과나 후속 ROLLBACK만으로 미반영을 확정하지 않고, 새 연결과 배타적 잠금 아래에서 판정한다.

**주요 위치:** `ingestion/services/ingestion-runs.service.ts`, 실행 Repository와 복구 통합 테스트.
**완료 조건:** 진행 중인 CLI를 중단으로 오인하지 않고 INTERRUPTED와 DB 반영 여부를 각각 판정한다.
**SPEC 참조:** 6.5절, 6.6절. **검증:** T3-36, T3-38~43.

### Step 24. CLI와 Cron에 공통 실행 기록 연결

**설명:** 기존 수집을 한 번 실행하면 이제 실행 기록과 결과도 함께 남게 한다.

- [ ] IngestionService의 접수, 시작, 단계, 저장 증거와 종료를 앞서 준비한 기능에 연결하고 CLI와 CRON을 구분한다.
- [ ] 같은 runId의 DB와 파일 로그, 실패 및 중복 실행, 기존 수집 재시도와 CLI 종료 코드를 검증한다. 영향받은 기존 테스트와 공통 준비 코드도 함께 맞춘다.
- [ ] 개발 환경의 API와 CLI를 같은 빌드로 맞추고 기존 자동 수집 설정과 스케줄러 등록을 확인한다.

**주요 위치:** `ingestion/services/ingestion.service.ts`, `policy-schedule.service.ts`, `apps/api/src/cli/import-policies.ts`.
**완료 조건:** CLI와 Cron의 실제 공통 흐름에서 실행 기록이 남고 정책 저장과 반영 증거가 함께 확정된다.
**SPEC 참조:** 6장. **검증:** T3-31~43.

### Step 25. 수집 상태와 실행 기록 조회 API

**설명:** 화면에서 현재 운영 상태, 기록 목록과 선택한 실행 상세를 각각 조회하게 한다.

- [ ] 실행 서비스와 저장소에 현재 상태, 마지막 정상 실행, 목록과 상세 조회를 연결한다.
- [ ] HTTP 부팅 복구와 Admin의 Ingestion 서비스 호출을 등록하고 세 GET API의 인증, query, 페이지와 오류 응답을 검증한다.

**주요 위치:** `admin/controllers/admin-ingestion.controller.ts`, `admin.module.ts`, 실행 서비스와 Repository.
**완료 조건:** CLI가 남긴 실제 DB 기록을 세 API로 확인하고 상태 불명을 정상 대기로 표시하지 않는다.
**SPEC 참조:** 6.5절, 7장. **검증:** T3-33, T3-40~43, T3-45, T3-48, T3-51.

### Step 26. 현재 수집 상태와 실행 상세 화면

**설명:** 관리자가 CLI나 자동 수집의 현재 상태와 결과를 웹에서 확인하게 한다.

- [ ] 관리자 메뉴와 수집 운영 페이지에 현재 상태 및 선택 실행 상세를 연결한다.
- [ ] 실행 결과, DB 반영 여부, 집계와 실패 원인을 구분하고 기본 실행 선택과 빈 상태를 표시한다.

**주요 위치:** 웹 `ingestion/`, 관리자 공통 메뉴, `admin.css`.
**완료 조건:** 실제 조회 API로 마지막 정상 시각과 실행 결과를 확인할 수 있다.
**SPEC 참조:** 8.3절. **검증:** T3-33, T3-35~37, T3-43, T3-45, T3-51.

### Step 27. 실행 기록 목록과 상세 선택

**설명:** 과거 수집 기록을 골라 같은 화면에서 결과를 다시 읽게 한다.

- [ ] 기록 목록, 페이지 이동, 선택 강조와 runId URL 복원을 상세 API에 연결한다.
- [ ] 현재 상태와 과거 상세를 분리하고 늦은 응답, 없는 ID, 영역별 오류와 재시도를 처리한다.

**주요 위치:** 웹 `ingestion/`의 기록 목록과 상세 선택 처리.
**완료 조건:** 목록 페이지 이동과 새로고침 후에도 선택 기준대로 상세를 조회하고 현재 수집 상태를 계속 확인한다.
**SPEC 참조:** 7.1절, 8.3절. **검증:** T3-48~49, T3-51.

### Step 28. 수집 조회 화면의 자동 갱신

**설명:** 수집 진행 상태는 새로 보되 관리자가 고른 과거 기록은 유지한다.

- [ ] 활성 실행의 반복 조회, 완료 반영, 탭 숨김과 복귀, 수동 새로고침을 연결한다.
- [ ] 선택과 페이지 유지, 겹친 조회 방지, 인증 만료, 429와 연결 오류를 브라우저에서 검증한다. 탭 복귀의 백그라운드 인증 재확인 중에도 기존 상세와 목록 페이지를 보존한다.

**주요 위치:** 웹 `ingestion/`의 조회 상태 관리와 브라우저 테스트.
**완료 조건:** 새로고침과 재진입에서 DB 상태를 복원하고 조회 실패를 수집 중단이나 0건으로 오인하지 않는다.
**SPEC 참조:** 8장 공통 인증, 8.3절. **검증:** T3-43~44, T3-49~51 중 조회 동작.

## 7. E. 웹 수동 수집 — Step 29~31

### Step 29. 웹 수집의 비동기 접수 API

**설명:** 웹은 실행 접수 응답만 먼저 받고 서버는 기존 수집을 계속 진행하게 한다.

- [ ] 공통 수집에 웹 접수 완료 신호를 연결하고 관리자 실행 POST에서 requestId와 처리자를 전달한다.
- [ ] 기록 확정 후 응답, 중복 접수, 접수 오류와 응답 유실, 연결 종료 후 작업 지속을 실제 HTTP로 검증한다. 같은 requestId의 접수 COMMIT 전 일시적 409와 동일 ID 상태 재확인도 재현한다.

**주요 위치:** `ingestion/services/ingestion.service.ts`, `admin/controllers/admin-ingestion.controller.ts`.
**완료 조건:** 수집 완료 전에 실행 ID를 반환하며 중복 요청에도 동일 실행을 확인할 수 있다.
**SPEC 참조:** 6.2절, 7.1절. **검증:** T3-28~30, T3-32.

### Step 30. 수집 시작 버튼과 접수 재확인

**설명:** 버튼을 누르면 바로 수집을 접수하고 진행 상태와 기록 목록에 연결한다.

- [ ] 서버의 현재 상태 조회를 기본으로 실행 안내, 접수와 중복 클릭 방지, 접수 후 상세 선택 및 목록 첫 페이지 갱신을 연결한다.
- [ ] POST 전 미확정 requestId를 sessionStorage에 저장하고, 새로고침과 재진입 및 재로그인 후 원래 요청을 추가 확인한다. 접수된 실행의 종료와 반영 상태가 명확할 때만 저장값을 정리한다.
- [ ] 저장소 오류, requestedRun=NULL, 일시적 409와 다른 CLI/Cron 실행에서 원래 ID를 보존하고 자동 POST를 막는다. 제한된 접수 확인과 수동 재조회, 명시적 재시도의 동일 ID 사용을 검증한다.

**주요 위치:** 웹 `ingestion/`의 수집 실행 처리.
**완료 조건:** 현재 수집 상태와 원래 요청의 접수 확인을 구분하며, 미확정 ID를 잃거나 새 ID로 자동 재요청하지 않고 결과를 확인한다.
**SPEC 참조:** 8.3절. **검증:** T3-28~30, T3-44, T3-50.

### Step 31. 세 수집 경로와 재시작 통합 검증

**설명:** 웹, CLI와 자동 수집이 겹치거나 서버가 재시작돼도 기록과 실제 작업이 맞는지 확인한다.

- [ ] 격리 환경에서 세 경로의 선점 순서, 중복 접수와 로그 및 실행 ID의 대응을 검증한다.
- [ ] 저장 전후 강제 종료, API 재시작 중 계속 실행되는 CLI와 종료 직후 새 접수의 경쟁을 재현한다.

**주요 위치:** 수집 HTTP, 독립 CLI, 스케줄러와 복구 통합 테스트.
**완료 조건:** 중복 수집 없이 실제 잠금과 실행 기록이 일치하고 반영 완료, 미반영과 확인 불가를 구분한다.
**SPEC 참조:** 6장, 8.3절. **검증:** T3-28~43, T3-50.

## 8. F. 최종 검증과 운영 전환 — Step 32~35

### Step 32. 전체 회귀와 검증 대응표 작성

**설명:** 각 기능을 합친 뒤 기존 서비스와 새 기능이 함께 동작하는지 확인한다.

- [ ] 전체 타입 검사, API 빌드와 API/DB 및 기존 웹 회귀 테스트를 실행하고 기존 공개, 검수, 수집 동작을 대조한다.
- [ ] T3-01~51의 검증 위치, 결과, 남은 인수 조건과 담당 Step을 대응표로 정리한다. 앞선 구현의 검증 누락은 보완하고 Step 33~35의 최종 웹 인수, 복원 및 운영 전환은 해당 근거가 나올 때까지 미실행으로 남긴다.

**주요 위치:** `apps/api/test/`, `apps/web/test/`, shared 테스트, MVP3 SUMMARY.
**완료 조건:** 전체 회귀가 통과하고 T3-01~51의 대응표에서 확인된 결과와 후속 미실행 항목을 구분한다. 전체 시나리오의 최종 충족 판정은 Step 35에서 한다.
**SPEC 참조:** 10장 전체. **검증:** T3-01~51의 대응표, 특히 T3-46 회귀. T3-47의 실제 복원은 Step 34.

### Step 33. 공개 및 관리자 웹 최종 인수

**설명:** 관리자가 실제 화면에서 검수하고 수집 결과를 확인하는 전체 흐름을 점검한다.

- [ ] 실제 API와 격리 DB에서 목록 탐색, 상세 복귀, 일괄 검수, 수집 시작과 기록 선택을 연결해 검수한다.
- [ ] 공개 탐색, 모바일, 키보드 조작, 인증 만료와 오류 이후 회복을 확인한다.

**주요 위치:** `apps/web/test/`의 공개 및 관리자 브라우저 검증.
**완료 조건:** 화면의 핵심 흐름과 오류 안내가 SPEC 및 실제 DB 결과에 일치한다.
**SPEC 참조:** 8장, 9장. **검증:** T3-14~17, T3-24~25, T3-28~30, T3-43~46, T3-49~51.

### Step 34. 백업 복원과 전환 절차 재현

**설명:** 기존 데이터를 보존한 채 새 버전으로 전환하고 다시 복원할 수 있는지 확인한다.

- [ ] MVP2 운영 절차를 바탕으로 실행 요약을 포함한 DB와 로그를 별도 빈 DB에 복원해 대조한다.
- [ ] 별도 환경에서 쓰기 중단, Migration, 새 API와 CLI 전환 및 첫 수집을 재현하고 필요한 절차를 MVP3 OPERATIONS에 기록한다.
- [ ] 실제 복원과 전환 근거를 Step 32의 대응표에 반영하고 최종 판정에 필요한 잔여 항목을 명시한다.

**주요 위치:** 기존 백업과 복원 검증기, `docs/mvp-3/OPERATIONS.md`.
**완료 조건:** 공개 UUID, 검수 이력, 실행 결과와 로그가 보존되며 전환 순서를 재현할 수 있다.
**SPEC 참조:** 5.3절, 9장. **검증:** T3-27, T3-33~34, T3-47.

### Step 35. 대상 환경 적용과 최종 인수

**설명:** 검증한 버전을 실제 사용할 환경에 반영하고 화면에서 운영 준비를 확인한다.

- [ ] 대상 DB와 기존 스케줄 설정을 확인하고 최신 백업 후 쓰기를 중단해 Migration과 API 및 CLI를 함께 전환한다.
- [ ] 첫 수집과 기록 조회, 공개 데이터 보존, 단일 API 및 기존 Cron 설정을 확인하고 SUMMARY와 전체 완료 기준을 맞춘다.
- [ ] Step 34의 백업 복원과 전환 검증 및 Step 33의 웹 인수 근거를 포함해 T3-01~51의 최종 충족 여부를 판정한다. 실패나 필수 미실행이 남으면 전체 완료로 표시하지 않는다.

**주요 위치:** 실행 환경, MVP3 OPERATIONS와 SUMMARY, 이 PLAN의 완료 체크.
**완료 조건:** 최신 화면에서 MVP3를 사용할 수 있고 실제 실행 결과와 정상 수집 시각, 오류 확인 및 복원 절차가 남아 있다. T3-01~51의 필수 조건에 미해결 실패와 미실행이 없다.
**SPEC 참조:** 9장, 10장. **검증:** T3-01~51 최종 충족 판정, 특히 T3-33, T3-46~47 및 전체 인수 결과.

## 9. 전체 완료 기준

- [ ] 전체 원본 필드의 중요도 분류와 미분류 처리가 목록 및 상세에서 일치한다.
- [ ] 전체 후보 기준의 필터와 정렬, 페이지 및 탐색 상태 복원이 동작한다.
- [ ] 일괄 검수의 확인, 부분 성공과 결과 재조회가 기존 개별 검수 안전성을 유지한다.
- [ ] CLI, Cron과 웹 수집이 같은 잠금과 실행 기록을 사용한다.
- [ ] 현재 수집 상태, 선택한 실행 상세와 페이지별 기록 목록을 실제 DB에서 조회한다.
- [ ] 재시작과 연결 오류에도 실행 결과와 DB 반영 여부를 구분하고 확정된 데이터를 보존한다.
- [ ] 공개 탐색, 관리자 인증, 개별 검수와 기존 수집의 회귀가 통과한다.
- [ ] T3-01~51의 검증 근거, 백업 복원과 대상 환경 전환 결과가 기록돼 있다.
