## 2. A. 기준 확인과 데이터 준비 — Step 1~4

### Step 1. 기존 구현과 MVP2 기준 확인

- [x] PRD·아키텍처·SPEC과 기존 수집·저장·테스트 코드를 대조해 재사용 위치와 불일치를 확인한다.
- [x] MVP1 검증 결과를 확인하고 MVP2 SUMMARY에 시작 상태와 남은 문제를 기록한다.

**완료·검수:** 최신 기준 문서가 준비되고 기존 기능의 현재 상태를 설명할 수 있다.

### Step 2. 관리자 API 타입과 입력 검증

- [x] 관리자 인증·검수·누락 API의 공용 요청/응답 타입과 Zod 검증을 정의한다.
- [x] 해시·거절 사유·페이지·필터·NULL·추가 필드의 정상/오류 입력을 테스트한다.

**완료·검수:** SPEC의 계약과 일치하며 잘못된 입력을 거부하고 기존 공개 타입은 유지한다.
**SPEC 검증:** T2-31, T2-41

### Step 3. 수집 원본과 검수 데이터 모델

- [x] source_policies·policy_reviews 엔티티와 관계·기본값·제약을 정의한다.
- [x] missing_count·실제 수집 시각·스냅샷·대기 유일성·상태별 필수값을 확인한다.

**완료·검수:** 타입·관계 정의 검증이 통과하고 세 데이터의 관계가 명확하다. 실제 스키마 차이 검증은 Step 4에서 수행한다.

### Step 4. 테이블 생성과 기존 정책 이관

- [ ] 한 Migration에서 새 테이블·제약·인덱스를 만들고 기존 공개본을 초기 원본으로 복사한다.
- [ ] 부분·DESC 인덱스는 Migration SQL로 생성하고 엔티티의 해당 인덱스에 `synchronize: false`를 지정한다. ORM 스키마 차이 0건과 DB 인덱스 방향·조건·유일성을 확인한다.
- [ ] 별도 검증 DB에서 정상 이관·빈 DB·해시 불일치·중복·중간 실패의 전체 취소를 검증한다.

**완료·검수:** 기존 공개 UUID·전체 행·지역은 그대로이고 초기 검수는 0건이다. 실패 시 부분 이관이 없다.
**SPEC 검증:** T2-01~02

## 3. B. 수집과 검수 후보 관리 — Step 5~14

### Step 5. 수집 원본 조회·저장

- [ ] 원본 일괄 조회·정렬된 행 잠금·묶음 저장을 구현한다.
- [ ] 전달받은 트랜잭션 관리자를 사용해 첫/최근 수집 시각·중복 식별자·누락 횟수 갱신을 검증한다.

**완료·검수:** 같은 트랜잭션에서 읽고 쓰며 취소 시 원본 전체가 이전 상태로 돌아온다.

### Step 6. 검수 후보와 스냅샷 보관

- [ ] 대기·거절 이력 일괄 조회와 변경본·공개 기준본 스냅샷 저장을 구현한다.
- [ ] 기존 대기를 먼저 대체한 뒤 새 후보를 넣고 과거 이력·스냅샷이 변하지 않는지 확인한다.

**완료·검수:** 원본 하나의 대기는 최대 한 건이고 이후 원본 변경에도 검수 당시 내용이 남는다.
**SPEC 검증:** T2-34

### Step 7. 공개 본문 저장과 조회수 갱신 분리

- [ ] 승인본의 공개 저장과 수집 조회수만 갱신하는 메서드를 구분한다.
- [ ] 기존 공개 UUID를 유지하고 조회수 변경 시 본문·raw_json·내용 해시가 바뀌지 않는지 확인한다.

**완료·검수:** 본문은 승인 경로로만 변경할 수 있고 최신 조회수는 별도로 반영할 수 있다.
**SPEC 검증:** T2-13

### Step 8. 수집 결과와 누락 판정

- [ ] 이번 응답과 지난 원본을 비교해 NEW·CHANGED·UNCHANGED·MISSING을 계산한다.
- [ ] 조회수만 변경·전체 0건·연속 누락·같은 날 재실행·재등장·정수 상한을 테스트한다.

**완료·검수:** 정상 전체 수집 횟수로 missing_count를 세고 다시 관찰되면 0이 된다.
**SPEC 검증:** T2-03, T2-13, T2-16~17, T2-19~20

### Step 9. 검수 후보 생성·유지·교체 판단

- [ ] 최신 원본·현재 공개본·대기·거절 이력으로 후보 생성·유지·대체 여부를 판단한다.
- [ ] 공개본 복귀·거절본 복귀·과거 승인/대체 해시 복귀와 공개 기준 변경을 테스트한다.

**완료·검수:** 같은 내용은 중복 대기를 만들지 않으며 공개본과 이력에 따라 최신 후보만 검수한다.
**SPEC 검증:** T2-06~12, T2-28

### Step 10. 수집분 일괄 저장 연결

- [ ] 원본 우선 잠금 후 수집 결과·누락·후보 판단을 실행하고 원본·후보·조회수를 함께 저장한다.
- [ ] 같은 QueryRunner의 단일 트랜잭션과 묶음 쓰기를 적용한다.

**완료·검수:** 일부 실패는 전체 취소되고 미승인 신규·변경 본문은 공개되지 않는다.
**SPEC 검증:** T2-04~05

### Step 11. 기존 CLI를 새 수집 흐름으로 전환

- [ ] 기존 전체 수집·검증·변환 이후 새 저장 서비스를 호출하고 결과 로그를 연결한다.
- [ ] 기존 수집 잠금·호출/재시도 규칙·종료 코드를 유지하며 이관 동일 자료와 조회수 변경을 확인한다.

**완료·검수:** CLI에서 원본·검수·누락·조회수가 SPEC대로 반영되고 로그가 수집 확정과 공개 승인을 구분한다. 기존 수집·저장·CLI 통합 테스트의 저장 기대값도 이 Step에서 새 흐름으로 갱신해 전체 API 테스트를 통과시킨다. 테스트를 건너뛰거나 Step 38로 미루지 않는다.
**SPEC 검증:** T2-03~05, T2-13~14, T2-18, T2-44

### Step 12. 수집 저장 실패와 재시도 검증

- [ ] 후반 묶음의 제약 오류로 앞 묶음까지 취소되는지 실제 DB에서 확인한다.
- [ ] 교착·직렬화 충돌에서 정해진 한도 내 재시도하고 최신 상태를 다시 읽어 계획을 계산한다.

**완료·검수:** 원본·후보·조회수의 부분 저장이 없고 재시도 대상 밖의 오류는 반복하지 않는다.
**SPEC 검증:** T2-21~22

### Step 13. 수집 로그·연결 장애와 종료 정리 검증

- [ ] COMMIT 전후 로그 실패·연결 끊김·확정 결과 불명을 재현한다.
- [ ] 로그 기록과 별개로 잠금·연결을 반환하고 이미 확정된 저장을 반복하지 않는지 확인한다.

**완료·검수:** saved와 확정 건수가 실제 상태를 반영하고 다음 수집이 실행 가능하다.
**SPEC 검증:** T2-44

### Step 14. 동시 수집과 공개 조회 검증

- [ ] 실제 CLI 두 개로 중복 실행·강제 종료 후 재실행을 확인한다. 스케줄러와 CLI의 경쟁은 Step 36에서 같은 잠금으로 추가 검증한다.
- [ ] 수집 대기·저장 중 기존 공개 검색·상세가 정상 응답하는지 검증한다.

**완료·검수:** 한 CLI만 수집하며 공개 조회는 확정된 정책을 계속 제공한다.
**SPEC 검증:** T2-23, T2-45

## 4. C. 관리자 인증 — Step 15~19

### Step 15. 관리자 자격 설정과 비밀번호 검증

- [ ] 단일 관리자 설정 검증과 내장 scrypt 기반 비밀번호 확인을 구현한다.
- [ ] 비밀값을 노출하지 않는 해시 준비 방법과 정상/오류 설정·비밀번호 경계를 테스트한다.

**완료·검수:** 잘못된 자격은 구분 없는 인증 오류이며 관리자 설정 검증을 수집 CLI에 강제하지 않는다.
**SPEC 검증:** T2-36, T2-40

### Step 16. 관리자 인증 쿠키

- [ ] 쿠키 발급·서명 검증·8시간 만료·삭제 속성을 구현한다.
- [ ] 변조·길이·형식·관리자 ID·발급/만료 경계를 테스트한다.

**완료·검수:** 인증값에 비밀번호가 없고 변조·만료 쿠키가 거부된다.
**SPEC 검증:** T2-36~37

### Step 17. 관리자 서버 권한과 요청 출처 검사

- [ ] 관리자 모듈과 Guard를 등록하고 보호 데이터 접근 전에 인증을 검사한다.
- [ ] 상태 변경 Origin 검사와 HTTP 전용 설정 검증을 연결한다. 수집·Migration·시드 CLI는 관리자 자격 없이 실행되는지 확인한다.
- [ ] `.env.example`과 `compose.yaml`의 api 서비스에 ADMIN_USERNAME·ADMIN_PASSWORD_HASH·ADMIN_AUTH_SECRET·ADMIN_WEB_ORIGIN 전달을 추가한다. 실제 비밀값은 문서·이미지에 넣지 않는다. Compose 보간 단계에서 자격 누락으로 CLI까지 막지 않도록 하고 필수 자격 검증은 HTTP 시작점에서 수행한다.
- [ ] 공통 오류 필터가 관리자 업무 코드와 안전한 메시지를 보존하고 기존 400·500·503 코드를 유지하는지 확인한다.

**완료·검수:** 무인증 데이터 요청은 401, 잘못된 출처는 403이며 공개 API 보호 설정은 유지된다.
**SPEC 검증:** T2-36, T2-38, T2-40

### Step 18. 로그인·인증 확인·로그아웃 API

- [ ] 로그인·me·로그아웃을 입력 검증·인증 쿠키·출처 검사에 연결한다.
- [ ] 공개·관리자 일반 호출 제한을 별도 집계하고 로그인 추가 제한을 적용한다. 공개 120회 소진 상태에서도 관리자 한도가 남은 인증 GET이 200인지 검증한다.
- [ ] 만료·쿠키 삭제·캐시 금지·비밀값 비노출을 통합 테스트한다. 이 Step의 me GET으로 한도 분리를 검증하고 Step 22의 검수 목록 GET에서도 추가 확인한다.

**완료·검수:** 정상 로그인부터 로그아웃까지 동작하며 잘못된 자격·요청 과다·만료가 SPEC대로 처리된다.
**SPEC 검증:** T2-36~37, T2-39

### Step 19. 웹 프록시를 통한 인증 검증

- [ ] 실제 웹 프록시의 Origin·Set-Cookie 전달과 쿠키 경로를 확인한다.
- [ ] JSON·본문 한도·로그 비노출·기존 공개 요청 보호의 회귀를 검증한다.

**완료·검수:** 웹 경유 인증이 동작하고 출처를 임의 보충하거나 내부 주소로 바꿔 우회하지 않는다.
**SPEC 검증:** T2-36~40

## 5. D. 검수·누락 API — Step 20~28

### Step 20. 검수 변경 내용 비교

- [ ] 공개 기준본과 검수 변경본의 필드 차이를 계산한다.
- [ ] 추가·삭제·NULL·공백·중첩 객체·배열을 구분하고 inqCnt는 제외한다.

**완료·검수:** 키 순서가 일정하고 없는 필드와 NULL이 구분되며 실제 내용 차이가 숨겨지지 않는다.
**SPEC 검증:** T2-35

### Step 21. 승인 가능 여부와 충돌 판단

- [ ] 대기 상태·화면 해시·최신 원본·기준 공개 ID/해시를 확인하는 공통 규칙을 구현한다.
- [ ] 신규의 공개본 없음 조건과 누락 상태에서도 검수 가능한 조건을 테스트한다.

**완료·검수:** 오래된 원본·공개 기준은 충돌로 판단하고 누락만으로 검수를 막지 않는다.
**SPEC 검증:** T2-26~27, T2-32

### Step 22. 검수 목록·상세·이력 조회 API

- [ ] 필터·정렬·페이지·스냅샷 비교·현재 공개본·canReview를 조회해 보호 API로 제공한다.
- [ ] 과거 제목·스냅샷 유지·빈 결과·404·인증 선검사와 공개/관리자 한도 분리를 검증한다. 목록은 일반 조회, 상세 비교는 같은 읽기 시점을 유지한다.

**완료·검수:** 관리자가 후보와 당시 기준본을 확인할 수 있고 미인증 요청에는 데이터가 노출되지 않는다.
**SPEC 검증:** T2-34, T2-36, T2-41~42

### Step 23. 누락 정책 조회 API

- [ ] 미공개 신규·이관 후 미수집 원본·마지막 실제 수집 시각 NULL을 검증한다.

**완료·검수:** 누락 정책을 정확히 조회하며 이관 시각을 실제 수집 시각으로 대신하지 않는다.
**SPEC 검증:** T2-36, T2-41~42

### Step 24. 검수 승인과 공개 반영

- [ ] 원본→후보→공개본 잠금 후 조건과 스냅샷을 재확인하고 검수 내용을 공개한다.
- [ ] 공개 저장·APPROVED 기록을 한 트랜잭션으로 처리하며 기존 UUID와 최신 조회수를 유지한다.

**완료·검수:** 승인 기록 실패 시 공개 저장도 취소되고 승인된 본문은 검수 스냅샷과 일치한다.
**SPEC 검증:** T2-15, T2-24~25

### Step 25. 검수 거절과 이력 저장

- [ ] 같은 잠금·검수 조건 확인 후 사유·처리자·종료 시각을 기록한다.
- [ ] 거절 사유 검증·종료 후보 재처리 거부·공개본 보존을 확인한다.

**완료·검수:** 거절 이력은 남고 기존 공개 정책과 원본 내용은 변경되지 않는다.
**SPEC 검증:** T2-31, T2-33

### Step 26. 승인·거절 API 연결

- [ ] 처리 서비스를 관리자 경로에 연결하고 인증·Origin·본문·오류 응답을 적용한다.
- [ ] 정상 처리·오래된 화면의 409·잘못된 사유·중복 요청을 HTTP로 검증한다.

**완료·검수:** 화면이 확인한 해시로만 처리되며 충돌 요청은 업무 데이터를 바꾸지 않는다.
**SPEC 검증:** T2-24, T2-26~27, T2-31, T2-33

### Step 27. 동시 검수와 수집 경쟁 검증

- [ ] 별도 DB 연결로 승인 두 개·승인과 거절·수집 저장과 승인의 경쟁을 재현한다.
- [ ] 원본 우선 잠금·확정 순서·재요청을 검증한다. 공개 기준 충돌·이후 후보 조정은 방어 경로이므로 격리 테스트 DB의 공개 행 직접 변경으로 재현한다.

**완료·검수:** 한 요청만 처리되고 오래된 후보가 최신 원본·공개본을 덮어쓰지 않는다.
**SPEC 검증:** T2-28~30, T2-33

### Step 28. 공개 데이터 분리와 관리자 API 계약 검증

- [ ] 미승인·거절·누락 자료가 공개 목록·상세·분야에 섞이지 않는지 확인한다.
- [ ] 관리자 필터·페이지·오류·권한·출처와 로그 비노출을 전체 경로에서 점검한다.

**완료·검수:** 공개 계약은 그대로이며 관리자 API가 SPEC의 응답·입력 기준을 충족한다.
**SPEC 검증:** T2-36, T2-38, T2-41, T2-45
